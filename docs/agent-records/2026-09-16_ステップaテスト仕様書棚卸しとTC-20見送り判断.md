# ステップaテスト仕様書（未コミット下書き）の棚卸しとTC-20見送り判断

- 日付: 2026-09-16
- 担当: Claude（ken-collabostyleの指示のもと）

## 背景・目的

`docs/forms/tests/【クラウド版】注文書兼利用申込書（月額：契約変更）_テスト仕様書.md`（ステップaの実機確認項目TC-17〜TC-26を含む下書き、未コミットのまま残存）が、実際には完了している実機確認結果を反映しておらず「2章はすべて未実施」という古い記述のままだった。ステップeの実機確認依頼をきっかけにユーザーから「TC-17は区分を参照する必要がある」との指摘を受けたことを発端に、本書とプロジェクトの実施記録（agent-records）との突合・棚卸しを行った。

## 調査内容（Reasoning）

- 本書のTC-17（`isActiveMonthlyRecord`が「区分」を判定条件に含まない仕様相違の実害確認）と、[2026-09-02の実機確認記録](2026-09-02_フェーズ1ステップa_実機確認と対応.md#L42)のTC-17（区分=ベースのレコード欠落、`baseRecordMissing`で対応済み）が同名で別内容であることが判明。ID体系が本書と実施記録側で独立して採番されたことによる偶然の重複。
- ユーザーへ`isActiveMonthlyRecord`の仕様（区分を判定条件に含めない設計理由：ベース・オプション両方を明細に残すため）を説明し、仕様相違ではなく意図的設計であることを確認。本書のTC-17は「対応不要」で決着
- TC-18〜TC-26についても各実施記録と突合した結果、TC-20（DOM構造不一致時のフェイルセーフの実機確認）を除く全項目が2026-09-02に実機確認・対応済みと判明。[詳細計画](../plans/2026-08-25_フェーズ1ステップa_インスタンス名UIとkintone連携.md#L96)には「TC-01〜TC-26をすべて完了」とあるが、[TC-25・TC-26確認記録](2026-09-02_フェーズ1ステップa_TC-25_TC-26確認.md#L27)には「フェイルセーフのDOM構造不一致テスト（TC-20相当）は未実施のまま残存する」と明記されており、両記録は矛盾していた。より詳細な一次情報である後者を優先し、TC-20は実際には未実施と判断
- TC-20の対応要否をユーザーに確認

## 実施内容（Acting）

- テスト仕様書の該当箇所を更新
  - 冒頭の「2章はすべて未実施」という記述を削除し、棚卸し結果（TC-20以外はすべて実機確認済み）を明記
  - TC-17：解決済み（意図的設計、対応不要）として更新。実施記録側の同名TC-17との混同を避ける注意書きを追加
  - TC-18・TC-19・TC-21・TC-23：各実施記録の内容（発見した不具合・追加したフェイルセーフ・再確認結果）を反映し解決済みに更新
  - TC-22・TC-25：正常動作確認済み・対応不要に更新
  - TC-24：TC-18対応で兼用済み（追加対応不要）に更新
  - TC-26：確認済みに加え、2026-09-11の単位パーツ削除により項目自体が対象外化した旨を追記
  - TC-20：ユーザーへの確認結果を受け「実機テスト見送り」に更新
  - 「3. 前提条件」のquery固定値設定に関する記述も、設定・確認済みである実態に合わせて更新
- ユーザーに、TC-20（DOM構造不一致の疑似発生テスト）の実機確認を行うか見送るか確認したところ、**見送る**との回答（2026-09-16）

## 結果・観察（Observation）

- テスト仕様書の内容が実際の実施記録と整合する状態になった
- TC-20は実機での意図的なDOM改変テストを行わないままクローズ。対象のフェイルセーフ実装自体（`instanceSelectorInitFailed`・`cancelQuantityLockFailed`等のDOM構造不一致検知パターン）はコード上存在し、`npm run test`の対象外ではあるが、`document.getElementById`が`null`または想定外の型を返すケースを想定したtry-catch的なガード（`instanceof HTMLInputElement`等のチェック）は実装済みであることをコードレビューで確認済み（[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)の`lockInstanceNameField`・`setChangedQuantityFieldLocked`・`buildInstanceSelector`）

## 得られた知見・製品への示唆

- 実機確認結果を記録するドキュメントが複数箇所（詳細計画の完了節、個別の対応記録、独立したテスト仕様書）に分散していると、更新漏れによる矛盾が生じやすい。今後のフォームでは、実機確認項目とその結果は極力1箇所（テスト仕様書があればそこ）に集約し、対応記録側はテスト仕様書への相互参照リンクのみにとどめる運用が望ましい
- テストケースIDを複数のドキュメントで独立に採番すると、本件（TC-17の同名別内容）のような混同が起こりうる。今後複数のテスト仕様書・記録をまたぐ場合は、IDにドキュメント固有のプレフィックスを付ける等の命名規則を検討したい

## 未解決課題・申し送り事項

- TC-20（DOM構造不一致時のフェイルセーフの実機確認）は見送りのままクローズ。将来、コラボフォームのUIライブラリ（Mantine）のバージョンアップ等でDOM構造が変わった場合、この種のフェイルセーフが実際に機能するかは未検証のままである点に留意
