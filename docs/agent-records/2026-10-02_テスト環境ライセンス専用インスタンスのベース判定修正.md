# テスト環境ライセンス専用インスタンスのベース判定修正

- 日付: 2026-10-02
- 担当: 波多野（開発窓口） / Claude Code

## 背景・目的

年額版ステップaの検証環境での実機確認中、ユーザーより「同じ顧客番号にインスタンスが二つあり、最初のレコードがテスト環境ライセンスの場合に『選択されたインスタンスの契約情報が見つかりませんでした』エラーとなる」という不具合報告を受けた。月額版（フェーズ1、2026-09-16完了・クローズ済み）にも同一のロジック（`findBaseRecord`が区分=ベースのレコードのみを探す）があるため、同じ不具合が存在する可能性があるとユーザーから指摘があり、両フォームへの修正を実施した。

## 調査内容（Reasoning）

ユーザーからの説明：コラボフローには「テスト環境ライセンス」という、正規契約とは別契約のインスタンスで正規契約のオプションを全て試用できるライセンスがある。この場合、契約品目は基本的に「テスト環境ライセンス」の1行のみで、区分=ベースの行が存在しない。そのため、ベースレコードがなくてもインスタンスの選択・申請ができるべきで、`検索ID`（kintoneのクラウド契約管理DBの`検索ID`フィールド、値`"テスト環境ライセンス  クラウド版"`）で判別する方針が示された。

月額版はまだ本番稼働前（検証環境のみ）とのことで、破壊的変更も許容されるとの確認を得た。月額・年額で完全に同一の業務ルールのため、`contract-change-shared-logic.ts`に共通ロジックとして実装する方針とした。

## 実施内容（Acting）

1. `src/forms/contract-change-shared-logic.ts`に`TEST_ENV_LICENSE_SEARCH_ID`定数と`findBaseOrTestEnvLicenseRecord`関数を追加。区分=ベースのレコードを優先して探し、見つからない場合は`検索ID`がテスト環境ライセンスを示すレコードを代わりに返す
2. `monthly-contract-change-logic.ts`・`annual-contract-change-logic.ts`の両方に`searchId`フィールド（kintoneの`検索ID`）を`CONTRACT_DB_FIELD_CODES`・`ContractRecord`・`toContractRecord`に追加
3. 両ファイルの`findBaseRecord`の内部実装を、共通モジュールの`findBaseOrTestEnvLicenseRecord`を使うように変更（`buildCurrentContractSummary`は無修正のまま、テスト環境ライセンスレコード自身の法人名・種類２・数量（年額は契約終了日も）がそのまま表示される）
4. 両方のテストファイル・共通モジュールのテストファイルにテストケースを追加（ベース優先、テスト環境ライセンスへのフォールバック、いずれも一致しない場合のundefined、レコード0件等）

## 結果・観察（Observation）

`npm run lint` / `npm run typecheck` / `npm test`（70件）/ `npm run build`すべて通過を確認した。

## 得られた知見・製品への示唆

テスト環境ライセンスは区分（`区分`）の選択肢（ベース／オプション／オプション各種／フォーム／フォームOP）のいずれにも明確に対応しておらず、`検索ID`という別フィールドで識別する必要がある点は、クラウド契約管理DBのデータ設計上の癖として今後も注意が必要（[クラウド契約管理DB.md](../kintone/クラウド契約管理DB.md)に追記する余地あり）。また、月額版フェーズ1は実機確認・クローズ済みだったが、この種の「普段は発生しないデータパターン」の不具合は運用が進むまで顕在化しないことがあり、クローズ済みの機能でも継続的なフィードバックが重要という教訓を得た。
