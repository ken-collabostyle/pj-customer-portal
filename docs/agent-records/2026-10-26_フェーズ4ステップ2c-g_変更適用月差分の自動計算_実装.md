# フェーズ4 ステップ2c-g 変更適用月差分の自動計算

- 日付: 2026-10-26
- 担当: 波多野（開発窓口） / Claude Code

## 背景・目的

[フェーズ4計画](../plans/2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)フェーズ2cのステップg。2026-10-26に確定した算出式（変更適用月差分＝変更適用希望月の翌月から契約期限までの残月数、[実施記録](2026-10-26_フェーズ4フェーズ2c変更適用月差分の算出式確定.md)）に基づき、`fidChangeApplyMonthDiff`を自動計算・セットする。

## 調査内容（Reasoning）

契約期限は`ContractRecord.contractExpiry`（`YYYY-MM-DD`）としてステップaで取得済み、変更適用希望年月はステップdでデフォルト値セット済みであること、`form.<パーツID>.change`内では`parts.value`の書き換えが可能なことを確認した。ユーザー確認事項3件（差分0以下は補正せず申請不可、readOnly化する、契約期限が取得できない場合は警告のうえ申請不可）を反映した[詳細計画](../plans/2026-10-26_フェーズ4ステップ2c-g_変更適用月差分の自動計算.md)を提示し、ユーザー承認を得た。

## 実施内容（Acting）

`src/forms/annual-contract-change-logic.ts`
1. `parseContractExpiryMonth(contractExpiry)`：`YYYY-MM-DD`から年月を取り出す（不正なら`null`）
2. `computeChangeApplyMonthDiff(applyYear, applyMonth, contractExpiry)`：`（契約期限の年×12＋月）－（適用希望年×12＋月）`を返す（不正入力は`null`。0以下も補正しない）

`tests/forms/annual-contract-change-logic.test.ts`：上記2関数のテスト10件を追加（基本例5、年またぎ3、同月0、後月-1、12ヶ月、不正入力等）。

`src/forms/annual-contract-change.ts`
1. `currentContractExpiry`キャッシュ（`fidCurrentContractExpiry`の日付パーツ値は表示形式に依存し形式が保証できないため、パーツ値は読まない）
2. `applyInstanceData`：契約期限のキャッシュ更新、契約期限が取得できない場合の`contractExpiryMissing`設定・警告、末尾での算出
3. `updateChangeApplyMonthDiff`：算出して`fidChangeApplyMonthDiff`にセットし、ロックを適用（算出不能なら空文字）
4. `lockChangeApplyMonthDiffField`：`document.getElementById("fidChangeApplyMonthDiff")`のinputを`readOnly`化し、解約ロックと同じ背景色を適用。失敗時は`changeApplyMonthDiffLockFailed`を立てて初回のみ警告
5. `form.fidChangeApplyYear.change`・`form.fidChangeApplyMonth.change`で再計算、`form.fidChangeApplyMonthDiff.change`で再ロック（ステップbの案Aと同じ考え方）
6. `validateChangeApplyMonthDiff`：算出値が0以下なら警告して申請ブロック
7. `blockSubmissionIfDataIssueDetected`に`contractExpiryMissing`・`changeApplyMonthDiffLockFailed`を追加し、`form.confirm`/`form.submit`のチェーンに`validateChangeApplyMonthDiff`を連結

## 結果・観察（Observation）

- `npm run lint`は通過。`npm run typecheck`は初回に4件のエラー（`toNumberOrNaN(value: string)`に`parts.value`の型`unknown`を渡していた）。原因は引数型の不一致と明確だったため、引数を`unknown`で受けるよう修正し、再実行して通過を確認した
- `npm test`：80件成功（新規10件）。`npm run build`：`dist/forms/annual-contract-change.js`再生成
- 計画からの差分として、初期表示時のデフォルト年月セットに伴う`change`イベントが、契約期限未取得・DOM未確定の段階で算出・ロックを走らせ、ロック失敗を誤判定するリスクに備え、ガードフラグ`changeApplyMonthDiffReady`を追加した（`applyInstanceData`による初回算出後に有効化）。この懸念は推測に基づく予防措置で、実際に発火するかは未確認

## 得られた知見・製品への示唆

- 日付パーツの値形式に依存しないよう、計算にはパーツ値ではなくJS側のキャッシュを使う設計にした
- `fidChangeApplyMonthDiff`のロックは、実DOMのIDが想定どおり（パーツIDと同じ）かどうかが実機で確認できていない。ステップbの解約ロックと同様、値セットによる再描画でreadOnlyが外れる可能性もあるため、再ロックのイベントを併用している

## 未解決課題・申し送り事項

なし。ユーザーが検証環境で[計画](../plans/2026-10-26_フェーズ4ステップ2c-g_変更適用月差分の自動計算.md)「確認方法」の各項目を実機確認し、問題なしと確認した（2026-11-02）。これによりクローズした。

2c-h（新規追加時の「nヶ月分」商品の妥当性チェック）は別途、`按分月数`の取得方法の確定後に計画する。
