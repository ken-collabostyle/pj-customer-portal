# フェーズ1ステップa：実機確認（kintone-contract-dbプロキシ400エラー・TC-17）と対応

- 日付: 2026-09-02
- 担当: Claude（ken-collabostyleの指示のもと）

## 背景・目的

[実装](2026-09-02_フェーズ1ステップa_インスタンス名UIとkintone連携_実装.md)完了後、検証環境での実機確認をユーザーが実施。その過程で発生した2件の事象への対応記録。

## 調査内容（Reasoning）

### 事象1：`kintone-contract-db`呼び出しが`status=400`で失敗

ユーザーからブラウザコンソールのエラー（`kintone-contract-dbの呼び出しに失敗しました。status=400`）を共有された。[proxy-api.md](../collaboform-js-api/proxy-api.md)の仕様（外部APIの4xx/5xxは`.then()`に`success: false`で渡る）から、コラボフォームのプロキシ機構自体ではなく外部API（kintone）側が400を返していると推定。

ユーザーにNetworkタブのレスポンスボディ確認を依頼したところ、kintoneのエラーレスポンスは以下の通りだった。

```json
{
  "code": "CB_VA01",
  "message": "入力内容が正しくありません。",
  "errors": { "app": { "messages": ["必須です。"] } }
}
```

`app`のみが必須エラーとなっており`query`には言及がない（kintoneの`records.json`は`query`省略可・`app`必須のため）。ユーザーが`query`パラメーターを「リクエストボディ」に`{"query":"顧客番号=55"}`として設定していたことが判明したが、[proxy-api.md:133](../collaboform-js-api/proxy-api.md#L133)「HTTPメソッドがGET/HEAD/DELETEの場合、設定した値は外部APIに送信されない」の通り、`kintone-contract-db`はGETメソッドのため、リクエストボディの内容はそもそも送信されない。結果として`app`も`query`もkintoneに届いておらず、`app`必須エラーのみが返っていた。

[docs/kintone/README.md](../kintone/README.md)の設計（`app=73`・`query=顧客番号="<値>"`は「クエリパラメーター」欄に設定する想定）と実際の管理画面設定が異なっていたことが根本原因。

### 事象2：TC-17（区分=ベースのレコードが存在しない場合）

ユーザーが実機で「区分=ベースのレコードを意図的に削除」して確認したところ、法人名／現在契約プラン／現在契約ユーザー数が空欄のまま表示された。運用上は起こらない想定だが、kintone側の入力ミス等で発生しうるケースとの指摘。

コード（[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)の`applyInstanceData`）を確認したところ、`buildCurrentContractSummary`が`undefined`を返す場合は`console.error`を出力するのみで、利用者への通知や申請ブロックが行われない実装だった。DOM構造不一致時（`instanceSelectorInitFailed`）には`alert()`＋`form.confirm`/`form.submit`での申請ブロックというフェイルセーフがあるのに対し、このケースには未実装というギャップがあった。ユーザーに対応方針を確認し、同様のフェイルセーフを追加する方針で合意（承認済み）。

## 実施内容（Acting）

- 事象1：コード変更なし。ユーザーに管理画面の「クエリパラメーター」欄へ`app=73`・`query=顧客番号=55`（`顧客番号`はNUMBER型のためクオート不要）を設定し直すよう案内
- 事象2：[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)に修正を実施
  - 新規フラグ`baseRecordMissing`と専用メッセージ`BASE_RECORD_MISSING_MESSAGE`を追加（`instanceSelectorInitFailed`とは別名で管理し、混在させない）
  - `applyInstanceData`で`区分`="ベース"のレコードが見つからない場合、`baseRecordMissing = true`をセットしその場で`alert()`表示。見つかった場合（インスタンス切り替えで正常データに戻った場合）は`false`にリセット
  - `blockIfInstanceSelectorFailed`を`blockSubmissionIfDataIssueDetected`にリネーム・拡張し、`instanceSelectorInitFailed`・`baseRecordMissing`の両方をチェックして該当する方のメッセージで`alert()`＋申請ブロックするよう変更
  - `npm run lint` / `npm run typecheck` / `npm run test` / `npm run build`をすべて実行し成功を確認

## 得られた知見・製品への示唆

- [docs/kintone/README.md](../kintone/README.md)の設計ドキュメントに「クエリパラメーター」欄へ設定する旨明記していたにもかかわらず、実際の管理画面設定では「リクエストボディ」に設定されてしまった。GET時にボディが送信されない仕様はコラボフォームJS API文書には明記されているが、プロキシAPI管理画面のUI上でGETメソッド選択時に「リクエストボディ」欄の入力自体を無効化する、または警告を表示する等のUI改善があれば、この種の設定ミスを防止できる（製品改善要望候補）
- 「非公式な実装のリスクを、公式APIのフェイルセーフ（`form.confirm`/`form.submit`のfalse return）で受け止める」という設計パターンは、DOM依存の実装だけでなく「本来起こらないはずだがデータ不整合で起こりうるケース」全般に適用できる汎用パターンであることが今回のTC-17対応で再確認された。今後のステップ（b以降）でも、データ欠落・不整合が起こりうる箇所には同様のフェイルセーフ追加を検討する
