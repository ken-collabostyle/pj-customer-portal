# フェーズ4 ステップb 年額版変更後契約数デフォルト値と解約連動

- 日付: 2026-10-02
- 担当: 波多野（開発窓口） / Claude Code

## 背景・目的

[フェーズ4計画](../plans/2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)フェーズ1のステップb。年額版フォームに、月額版ステップbと同じパターン（「解約」チェックON時は変更後契約数を0固定・入力不可、OFF時は現商品契約数を再セット）を実装する。

## 調査内容（Reasoning）

月額版[ステップb計画](../plans/2026-09-02_フェーズ1ステップb_変更後契約数デフォルト値と解約連動.md)・[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)の実装を確認し、年額版フォームもパーツID（`fidProductCancel`・`fidChangedProductQuantity`・`fidCurrentProductQuantity`）が月額版と完全一致することを確認した。フェーズ4計画では本ステップを「フル年額商品のみ対象」としているが、商品マスタ連携（フェーズ2a）が未解消で「nヶ月分」商品の判定手段がないため、今回はすべての明細行に月額版と同じロジックを適用し、「nヶ月分」商品の除外はフェーズ2に先送りする方針を[詳細計画](../plans/2026-10-02_フェーズ4ステップb_年額版変更後契約数デフォルト値と解約連動.md)として提示、ユーザー承認を得た。

## 実施内容（Acting）

`src/forms/annual-contract-change.ts`に以下を追加した（月額版`monthly-contract-change.ts`のステップb実装を同じパターンで複製）。

1. 定数`CANCEL_CHECKBOX_PART_ID`・`CANCEL_CHECKED_VALUE`
2. `form.fidProductCancel.change`イベントハンドラー：解約チェックON時は変更後契約数を`"0"`固定、OFF時は現商品契約数を再セット
3. `setChangedQuantityFieldLocked`関数：DOM操作（ネイティブinputの`readOnly`切り替え）で変更後契約数入力欄をロック/アンロック
4. フェイルセーフ`cancelQuantityLockFailed`：DOM構造不一致時に立てて`blockSubmissionIfDataIssueDetected`で申請をブロック

`annual-contract-change-logic.ts`（純粋ロジック）・テストファイルの変更は不要（月額版ステップbと同様、DOM・collaboform API依存のロジックのため）。

## 結果・観察（Observation）

`npm run lint` / `npm run typecheck` / `npm test`（70件、変更なし）/ `npm run build`（`dist/forms/annual-contract-change.js`再生成）をすべて実行し通過を確認した。

なお、検証中に一時`npm test`が`Cannot read properties of undefined (reading 'config')`で3ファイルとも失敗する事象が発生したが、`node_modules/.vite`のvitestキャッシュが古くなっていたことが原因と判明。`npx vitest run --no-cache`で成功を確認後、通常の`npm test`でも再現しなくなった。コード側の問題ではない。

## 得られた知見・製品への示唆

月額版の解約連動ロジックはDOM操作部分も含めて年額版にそのまま移植でき、パーツID設計が月額版を踏襲した効果が確認できた。vitestのdepキャッシュが古くなると`describe`等のグローバルが解決できずテストスイート全体が失敗することがあるため、同様の謎のテスト失敗が再発した場合は`node_modules/.vite`のキャッシュクリアを疑うとよい。

## 追記（2026-10-02）：差分パーツの自動計算によるロック解除への対応

ユーザーの実機確認により、「解約」チェックON時にいったんグレーアウトするが、その後入力不可が解除される不具合が報告された。調査の結果、年額版のみに存在する「変更後差分契約数」（`fidChangedProductQuantityDiff`、`fidChangedProductQuantity`に依存する`calculate`型パーツ）が、解約連動での値セットをトリガーに自動再計算され、その際の行の再描画でJSが直接セットした`readOnly`が解除されることが原因と判明。

対応として、`form.fidChangedProductQuantityDiff.change`イベントをリッスンし、自動計算完了後に改めてロックし直す方式（ユーザー承認済みの「案A」、プロダクトと衝突しないコード側のみの対策）を実装した。解約チェック状態は新設のキャッシュ`cancelledRowState`で保持する。`npm run lint` / `npm run typecheck` / `npm test`（70件）/ `npm run build`で確認済み。

案Aで解決しない場合は、`fidChangedProductQuantityDiff`を`calculate`型から通常の数値パーツに変更し差分計算をJS側に移管する「案B」（フォーム構造変更を伴う）に切り替える方針。

## 未解決課題・申し送り事項

ユーザーによる検証環境での実機確認が未実施。解約チェックON/OFF連動（0固定・入力ロックが維持されること、複数行での独立動作）、および「nヶ月分」商品行でも同じ挙動になること（現時点で制限なしの暫定挙動）の確認が必要。案Aで解決しない場合は案Bへの切り替えを検討する。実機確認完了後、[計画ファイル](../plans/2026-10-02_フェーズ4ステップb_年額版変更後契約数デフォルト値と解約連動.md)のstatusをcompletedに更新し、本記録のstatusもresolvedにする。
