# フェーズ1ステップb：変更後契約数のデフォルト値／解約チェック連動（実装）

- 日付: 2026-09-02
- 担当: Claude（ken-collabostyleの指示のもと）

## 背景・目的

[全体計画](../plans/2026-08-24_顧客ポータルカスタマイズ全体計画.md)フェーズ1のステップbとして、明細行の「解約」チェックボックス（`fidProductCancel`）ON時に「変更後契約数」（`fidChangedProductQuantity`）を0固定・入力不可にし、OFF時は元の契約数（現商品契約数）を再セットする機能を実装する。事前に[詳細計画](../plans/2026-09-02_フェーズ1ステップb_変更後契約数デフォルト値と解約連動.md)をユーザー承認済み。

「変更後契約数」のデフォルト値（現商品契約数と同じ値をセット）自体はステップaで実装済みのため、本ステップは解約チェックとの連動部分のみが対象。

## 調査内容（Reasoning）

- パーツ構造JSON（[docs/forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json:158-167](../forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json#L158-L167)）で`fidProductCancel`の設定を確認。`checked_comment: "解約"` / `unchecked_comment: "継続"`。[parts-reference.md](../collaboform-js-api/parts-reference.md)の仕様通り、`parts.value`はチェック状態に応じてこれらの文字列で取得できることを確認
- [events-reference.md](../collaboform-js-api/events-reference.md)の`form.<パーツID>.change`イベントが明細パーツにも対応し、`data.row_index`で対象行を特定できることを確認（公式API）
- 「変更不可」化について、[parts-reference.md:101](../collaboform-js-api/parts-reference.md#L101)「`enabled`は取得のみ可能」により公式APIでは実現不可と判明。ステップaの`lockInstanceNameField`（[TC-19対応](2026-09-02_フェーズ1ステップa_TC-19プルダウン表示崩れ対応.md)）と同じDOM操作パターン（`readOnly`化）を踏襲する方針とした

## 実施内容（Acting）

[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)に以下を追加。

- 定数`CANCEL_CHECKBOX_PART_ID`（`fidProductCancel`）・`CANCEL_CHECKED_VALUE`（`"解約"`）を追加
- 新規フラグ`cancelQuantityLockFailed`と専用メッセージ`CANCEL_QUANTITY_LOCK_FAILURE_MESSAGE`を追加（他のフェイルセーフフラグとは別名で管理）
- 新規関数`setChangedQuantityFieldLocked(rowIndex, locked)`：明細テーブルの行インデックスから`table:{row}:fidChangedProductQuantity`のネイティブinputを取得し`readOnly`を設定。取得失敗時は`cancelQuantityLockFailed`を立てて`alert()`表示
- `form.fidProductCancel.change`イベントハンドラーを追加：`data.row_index`で対象行を特定し、チェック状態（`"解約"`か否か）に応じて同じ行の`fidChangedProductQuantity.value`を`"0"`または`fidCurrentProductQuantity.value`（現商品契約数）にセットし、`setChangedQuantityFieldLocked`で入力欄をロック/アンロック
- `blockSubmissionIfDataIssueDetected`に`cancelQuantityLockFailed`のチェックを追加
- `npm run lint` / `npm run typecheck` / `npm run test` / `npm run build`をすべて実行し成功を確認

## 得られた知見・製品への示唆

- チェックボックスパーツの`parts.value`はON/OFFのboolean値ではなく、フォーム設定の「チェック時／未チェック時の表示コメント」文字列で取得・判定する仕様。実装時はパーツ構造JSONで実際のコメント文字列を確認する必要がある（今回`checked_comment: "解約"`を使用）
- 「変更不可」化の要求がある場合、公式APIの`parts.enabled`は設定不可のため、DOM操作（`readOnly`）による非公式実装がステップaに続き必要になった。この対応パターン（対象ネイティブ要素をID規則から特定→readOnly切り替え→失敗時はフェイルセーフ）が本プロジェクトの標準パターンとして定着しつつある。明細テーブル内パーツの場合はID規則が`table:{row_index}:{パーツID}`になる点が単一パーツとの違い
