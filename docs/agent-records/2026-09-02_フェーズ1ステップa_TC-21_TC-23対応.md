# フェーズ1ステップa：TC-21（明細行数超過）・TC-23（kintone-contract-db呼び出し失敗）対応

- 日付: 2026-09-02
- 担当: Claude（ken-collabostyleの指示のもと）

## 背景・目的

ユーザーからTC-21〜TC-26の実機確認結果が一括で共有された。このうちTC-21・TC-23が「警告して申請できなくしましょう」という未対応の指摘、TC-24は同様の指摘だったが調査の結果[TC-18対応](2026-09-02_フェーズ1ステップa_実機確認と対応.md)で既に実装済みと判明。TC-22・TC-25・TC-26は「正常動作を確認」で対応不要。

## 調査内容（Reasoning）

- **TC-21**（明細行数がテーブル最大行数を超過）：[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)の`applyLineItemsToTable`は超過時に`console.warn`を出力するのみで、`alert()`・申請ブロックのフェイルセーフが未実装だった
- **TC-23**（kintone-contract-db呼び出し失敗：プロキシ側エラー・通信エラー）：`form.show`ハンドラー内、`response.success`が`false`の場合（プロキシ側エラー）と`.catch`の通信エラーの両方で`console.error`のみ、`alert()`・申請ブロックのフェイルセーフが未実装だった
- **TC-24**（取得0件）：同ハンドラー内の`instances.length === 0`分岐は、[TC-18対応](2026-09-02_フェーズ1ステップa_実機確認と対応.md)で`noActiveContractFound`フェイルセーフ（alert＋申請ブロック）を実装済み。kintoneの取得結果が0件の場合もこの分岐を通るため、追加対応不要と判断した

## 実施内容（Acting）

- [monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)に修正を実施
  - **TC-21**：新規フラグ`lineItemsExceedTableCapacity`と専用メッセージ`LINE_ITEMS_EXCEED_CAPACITY_MESSAGE`を追加。`applyLineItemsToTable`で明細行数がテーブル最大行数を超えた場合に`true`をセットし`alert()`表示、超えていなければ`false`にリセット
  - **TC-23**：新規フラグ`kintoneCallFailed`と専用メッセージ`KINTONE_CALL_FAILED_MESSAGE`を追加。`response.success`が`false`の場合と`.catch`の通信エラーの両方でこのフラグを`true`にし`alert()`表示
  - `blockSubmissionIfDataIssueDetected`に両フラグのチェックを追加
- `npm run lint` / `npm run typecheck` / `npm run test` / `npm run build`をすべて実行し成功を確認

## 結果・観察（Observation）

- `npm run lint`：エラーなし
- `npm run typecheck`：エラーなし
- `npm run test`：16件全て成功
- `npm run build`：`dist/forms/monthly-contract-change.js`再生成を確認
- 実機での再確認（TC-21・TC-23の状況を再現してalert表示・申請ブロックを確認）を**2026-09-02にユーザーが完了**。問題なし
- 本対応中も`npm test`を他コマンドと連続実行した直後に`Cannot read properties of undefined (reading 'config')`というvitestランナー起動時の一過性エラーが複数回再現した（[実機確認と対応](2026-09-02_フェーズ1ステップa_実機確認と対応.md)・[TC-19対応](2026-09-02_フェーズ1ステップa_TC-19プルダウン表示崩れ対応.md)でも同事象を観測済み）。単体で間隔を空けて再実行すると安定して16件成功するため、コード側の問題ではないと判断

## 得られた知見・製品への示唆

- `collaboform.proxy.call()`の失敗パターン（外部APIの4xx/5xx＝`response.success`が`false`、タイムアウト・通信障害＝`.catch()`）は、いずれもユーザー起因ではなくシステム側の異常であるため、データ不整合系のフェイルセーフと同じパターン（alert＋申請ブロック）を一律で適用するのが妥当という方針が今回で固まった。今後別フォームでも同種のkintone連携を実装する際は、この2種類の失敗パターンを最初からフェイルセーフ対象に含めることを標準化したい
- ユーザーから複数のテストケース結果がまとめて共有された場合、個別の指摘の中に「実は既存のフェイルセーフで対応済み」なものが混在することがある（TC-24）。実装前にコードを確認し、重複対応を避けることが重要

## 未解決課題・申し送り事項

- vitestランナー起動時の一過性エラー（`Cannot read properties of undefined (reading 'config')`）の再現条件は依然未解明（[TC-19対応](2026-09-02_フェーズ1ステップa_TC-19プルダウン表示崩れ対応.md)から持ち越し。テスト結果自体には影響しないため低優先度）
