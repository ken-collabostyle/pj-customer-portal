# フェーズ1ステップf：変更適用希望年月のデフォルト値・選択可能範囲（実装）

- 日付: 2026-09-02
- 担当: Claude（ken-collabostyleの指示のもと）

## 背景・目的

[全体計画](../plans/2026-08-24_顧客ポータルカスタマイズ全体計画.md)フェーズ1のステップfとして、変更適用希望年月（`fidChangeApplyYear`/`fidChangeApplyMonth`）に当月をデフォルトセットし、月末3営業日前以降は翌月以降のみ選択可能とする機能を実装する。事前に[詳細計画](../plans/2026-09-02_フェーズ1ステップf_変更適用希望年月デフォルト値と選択可能範囲.md)をユーザー承認済み。

## 調査内容（Reasoning）

- パーツ構造JSONで`fidChangeApplyYear`（`number_v2`型、2025〜2099の範囲）・`fidChangeApplyMonth`（`list`型、選択肢"1"〜"12"）を確認
- 「選べないようにする」の実現方法について、`fidChangeApplyMonth`がMantineのSelectコンボボックス（選択肢一覧は開いた時のみDOMにポータル描画）であり、選択肢自体を削除するDOM操作は非常に脆弱と判断。ユーザーと協議のうえ、**「確認」ボタン押下時（`form.confirm`/`form.submit`）に選択値を検証し、不可なら`alert()`＋ブロックする方式**を採用（ドロップダウン自体は全月選択可能なまま）
- 当月選択可能期限日の定義について、ユーザーと協議のうえ「当月の最終営業日から数えて3番目（3rd-from-last）の営業日」を基準日と決定
- 祝日データについて、[全体計画](../plans/2026-08-24_顧客ポータルカスタマイズ全体計画.md)の確定方針「外部APIは使わず静的データとしてJS内に保持する」に基づき、固定日祝日・ハッピーマンデー祝日（一意に算出可能）に加え、春分の日・秋分の日は広く使われる近似式（1980〜2099年有効）で算出。振替休日・国民の休日（前後を祝日に挟まれた日。例：2026-09-22）のルールも反映
- 祝日データの保持範囲はユーザーと協議のうえ2026〜2035年（10年分）に決定。手計算のミスを避けるため、Node.jsスクリプトで実装と同一ロジックを実行し値を検証してから静的テーブルに埋め込んだ

## 実施内容（Acting）

- 新規：[src/forms/japan-holidays.ts](../../src/forms/japan-holidays.ts)：2026〜2035年の日本の祝日データ（`JAPAN_HOLIDAYS`）。算出方法・更新方法をファイル冒頭にコメントで明記
- [monthly-contract-change-logic.ts](../../src/forms/monthly-contract-change-logic.ts)に純粋関数を追加：`isBusinessDay`・`getBusinessDaysOfMonth`・`getCutoffBusinessDay`・`computeEarliestAllowedApplyMonth`・`isApplyMonthSelectionAllowed`

  - `form.show`の先頭（kintone連携処理とは独立、プロキシ呼び出し完了を待たず即時実行）で`fidChangeApplyYear`/`fidChangeApplyMonth`にデフォルト値をセット
  - 新規関数`validateChangeApplyMonth(data)`：選択値が最早選択可能年月以上かを検証し、不可なら`alert()`表示
  - `form.confirm`/`form.submit`のハンドラーを、既存の`blockSubmissionIfDataIssueDetected()`と`validateChangeApplyMonth(data)`の両方を呼ぶ形に変更

## 得られた知見・製品への示唆

- 「選択肢自体を制限する」という要求に対し、対象パーツがMantineの動的レンダリングコンポーネント（ドロップダウンを開くまでDOM未生成）の場合、DOM操作での制限は非常に脆弱。代わりに「確認・送信タイミングでの検証＋ブロック」という、公式APIのみで完結する設計で同等の業務要件を満たせることが今回のステップfで確立できた。ステップaで確立した「非公式実装の失敗を公式APIでブロックする」パターンをさらに発展させ、「そもそも非公式DOM操作を使わずに公式APIのみでブロックする」という、より堅牢な代替パターンとして今後のステップでも優先的に検討したい
- 祝日データのように「正確な値の算出に複雑なロジック（近似式・振替休日・国民の休日等の組み合わせ）が必要」なケースでは、手計算でハードコードするとミスのリスクが高い。実装ロジックと同一のアルゴリズムを一時スクリプトで実行し、出力を検証してから静的データとして埋め込む手法が有効だった（今回、この検証によって「国民の休日」ルールの実装漏れ（2026年9月22日等）を事前に発見できた）
- 春分の日・秋分の日は近似式による予測値である旨をコード内コメントで明記した。特に2026年9月は今回の実装直後に実機確認が行われる月であり、近似式の精度がそのまま初回の実機確認結果に影響する
