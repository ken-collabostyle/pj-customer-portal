# フェーズ4 フェーズ3 サブドメイン2パーツは残し、取得元は「プレイス_サブドメイン管理アプリ」と確定

- 日付: 2026-11-18
- 担当: 波多野（開発窓口） / Claude Code

## 背景・目的

2026-11-09に「コラボフォーム（★2・★3）の処理とサブドメインのセットは不要」と確定していた。その後、ユーザーが年額版の最新パーツ構造JSON・Excelを更新し、規約合意系パーツの削除状況とサブドメイン2パーツの扱いを突合した。

## 調査内容（Reasoning）

最新の年額版JSON（`total_count` 35→33）との差分：

- 削除：`fidCollaboformTermsOnContract`、`fidCollaboformTermsOnCancel`（規約合意系）
- 残存：`fidCollaboflowTermsAgreement`（コラボフロー規約への同意）、`fidCollaboformSubdomain`、`fidCollaboformCurrentSubdomain`
- 変更：`fidAddedProductName` に `master_parts_key`・`master_id` が追加（意図は未確認）

## 確認結果

ユーザーの回答（2026-11-18）：

1. `fidCollaboflowTermsAgreement`（コラボフロー規約への同意）は一旦残す。
2. **サブドメイン2パーツ（`fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain`）は残す。** これらは使用しているコラボフローインスタンスに紐づいており、**kintoneの「プレイス_サブドメイン管理アプリ」から取得する**ことになった。
3. 矛盾する指示があれば、この回答が最新とする。

## 実施内容（Acting）

ドキュメントのみ更新（コード変更なし）。

- 年額版パーツID設計：削除済み2パーツを除外し、経緯を追記
- 11-09の実施記録：未解決課題に、年額版の突合結果と本記録への参照を追記
- 実装メモ（年額・月額）、フェーズ4計画、全体計画、kintone README：11-09の「サブドメインのセットは不要」が本記録で上書きされた旨を追記

## 結果・観察（Observation）

- 11-09の確定事項のうち、「規約合意系の処理が不要」は維持される。「サブドメインのセットが不要」は**取り消され、サブドメインのセットが実装対象に戻る**。
- コードは現状、サブドメイン2パーツを参照していない。新規実装が必要になる。

## 得られた知見・製品への示唆

- サブドメインはコラボフローのインスタンス単位の情報で、kintoneの契約管理DBではなく専用アプリが取得元になる。
- 既存のkintone連携（クラウド契約管理DB・ライセンス種類マスタ・商品マスタ）に、サブドメイン管理アプリのプロキシAPI追加が必要になる見込み（コラボフォームのプロキシAPIはアプリ単位の設定）。

実装の詳細計画に入る前に、次の確認が必要。

1. ~~アプリ情報~~：**【2026-11-18回答済み】アプリID 81、APIキー認証、フィールド定義は[docs/kintone/json/プレイス_サブドメイン管理.json](../kintone/json/プレイス_サブドメイン管理.json)（整理は[プレイス_サブドメイン管理.md](../kintone/プレイス_サブドメイン管理.md)）。`.env`のキー名とプロキシAPI名は未定**

4. 2パーツの役割：申込み時（`fidCollaboformSubdomain`）と解約時（`fidCollaboformCurrentSubdomain`）で取得内容に違いがあるか。パーツは表示・編集可否のどちらか

## 追加回答（2026-11-18、ユーザー）

上記の未解決課題への回答：

- 検索キーは `インスタンス名`。`ユーザー削除日` が空のレコードのみ対象とし、それでも複数ある場合はエラーとする。
- セットはコラボフォームの**契約・新規追加・解約時のみ**。申込み時と解約時の2パーツに違いはない。
- 月額版・年額版の両方に適用する。
- プロキシAPIは管理画面での作成をユーザーが行う。名称は提案する（`kintone-place-subdomain`・`kintone-place-subdomain-annual`）。`.env.example` へのキー追加は承認済み。
- `fidAddedProductName` の `master_parts_key`・`master_id` は入っているのが正（以前が誤り）。対応不要。

残る未確認事項は、コラボフォームの契約・新規追加・解約の判別方法、セットのタイミング、エラー時の挙動など。[詳細計画](../plans/2026-11-18_フェーズ3追加_コラボフォーム契約時のサブドメイン取得とセット.md)のQ1〜Q5で確認する。

## 追加回答2（2026-11-18、ユーザー）

- コラボフォームの契約・新規追加・解約の**判別はしない**。サブドメイン管理アプリに選択中インスタンスのレコードがあれば、常に取得してセットする（コラボフォームの契約情報があれば取ってくる）。判別が不要になるため、上記の「コラボフォームの契約・新規追加・解約時のみ」は上書きされた。
- [詳細計画](../plans/2026-11-18_フェーズ3追加_コラボフォーム契約時のサブドメイン取得とセット.md)を更新済み。残る確認は、取得のタイミング（案：インスタンス確定時）、セット先（案：両パーツに同じ値）、0件・複数件・通信失敗時の挙動（案：0件は空のまま、複数件と通信失敗はブロック）、編集可否。

## 追加回答3（2026-11-18、ユーザー）：サブドメインは手入力で進める

- 取得元をプレイス_サブドメイン管理アプリとする方針は変えないが、インスタンス名をJS側から渡す方式は、他社のサブドメインを参照できてしまうため**許容できない**。このため、**サブドメインは手入力で進める**。
- 将来、同アプリに「顧客番号」を追加できれば、プロキシ側でユーザー拡張属性の顧客番号とマッチングして安全に取得できる。可否は、ユーザーが別途業務支援チームに確認する。
- 影響：サブドメイン2パーツ（`fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain`）の自動セットは実装しない。コード変更は発生しない。[詳細計画](../plans/2026-11-18_フェーズ3追加_コラボフォーム契約時のサブドメイン取得とセット.md)は `on-hold` にした。
- 留意点：ユーザー拡張フィールドをプロキシに差し込む機能は、コラボフォームに未実装だった（[README](../kintone/README.md)、2026-08-25時点）。顧客番号を追加できても、この機能が使えることが前提になる。
- 本記録のステータスは、業務支援チームの確認結果が出るまで `open` のままにする。
