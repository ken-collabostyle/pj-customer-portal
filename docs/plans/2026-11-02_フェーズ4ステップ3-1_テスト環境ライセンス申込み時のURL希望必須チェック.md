## 事前調査の結果（Reasoning）

| 項目 | 状態 |
| --- | --- |
| 対象パーツ | 3パーツとも`type: text`、`max_length: 20`、`required: false`、`display: true`（パーツ構造JSON）。常時表示されており、現状は未入力でも申請できる |
| 判別に使う値 | `fidAddedProductCode`は明細テーブル（`tbl_1`）の列で、`fidAddedProductName`のlookupで自動セットされる。ステップ2c-hの`validateAddedProductProratedMonths`でも同じ列を読んでいる |
| 必須の動的切り替え | コラボフォームのJS APIには、パーツの`required`を動的に切り替える手段がドキュメント上見当たらない（使えるのは値の読み書きと`display`）。そのため、他のステップ（2c-g・2c-h等）と同じく、`form.confirm`/`form.submit`で未入力を検出して申請をブロックする方式を採用する |
| 既存契約のテスト環境ライセンス | 既存契約側は`検索ID`で判別している（`TEST_ENV_LICENSE_SEARCH_ID`）が、本ステップは「新規追加された場合」が対象のため、新規追加行のみを判定対象とする |

## 検証ルール（提案）

本ステップでは、次の2つの検証を追加する。

### A. 新規追加行の数量チェック（全商品が対象）
1. 対象行：新規追加行のうち、**商品が選択されている行**（`fidAddedProductCode`または`fidAddedProductName`が空でない行）
2. 対象行の追加商品契約数（`fidAddedProductQuantity`）が、未入力・空白のみ・数値でない・0以下・小数の場合は、`alert()`＋申請ブロック（数量を入力するよう促す）
3. 文言案：「追加商品『○○』の追加商品契約数が未入力または0です。1以上の数量を入力してください。」（最初に見つかった1行を対象に表示）
4. 商品が選択されていない行は、数量が入力されていても対象外（本ステップでは扱わない）

### B. テスト環境ライセンス追加時のURL希望必須チェック（★1）
1. 新規追加行のうち、`fidAddedProductCode`に`CCTLST0000`が含まれる行を「テスト環境ライセンス行」とする。商品コードのみで判定し、数量には依らない
2. テスト環境ライセンス行が1行でもある場合、`fidTestEnvUrlFirstChoice`・`fidTestEnvUrlSecondChoice`・`fidTestEnvUrlThirdChoice`のすべてが入力済み（空・空白のみでない）でなければ、`alert()`＋申請ブロック
3. 文言案：「テスト環境ライセンスを追加する場合は、テスト環境のURL希望①〜③をすべて入力してください。（未入力：テスト環境のURL希望②、③）」（未入力の項目名を列挙する）
4. テスト環境ライセンス行がない場合は、対象外（従来どおり）

警告は1回の確認・送信操作で1つずつ表示する（A→Bの順）。

### 数量チェックの検討（論理的矛盾の有無）

「商品が選択されたすべての新規追加行で、数量が未入力・0なら警告する」という方針について、既存の仕様・実装と矛盾しないかを検討した。**矛盾は見つからなかった**。

| 観点 | 検討結果 |
| --- | --- |
| `fidAddedProductQuantity`の必須設定 | `required: false`。現状は商品を選択して数量が空のまま申請でき、価格（数量×単価）が0になる。これは実質的な抜けであり、本チェックはそれを埋める |
| ステップc（オプションのユーザー数整合性） | オプション系の新規追加行は、ベース行がある場合、数量がベースと一致しなければブロックされる（0・未入力も不一致）。そのため、オプション系商品はすでに部分的にカバーされている。一方、オプション以外（フォーム等）の商品や、ベース行が解約されている場合はカバーされておらず、本チェックが補完する。両者は同時に成立し、矛盾しない（数量0のオプション行は両方の警告対象になるが、警告は1つずつ出るため問題ない） |
| 2c-h（按分月数チェック） | 商品コードのみで判定しており数量には依らない。本チェックと独立。警告の順序は、数量の警告を先に出し（A）、按分月数の警告は後に出る形でも、先でもよい（本計画では2c-hの直後に連結し、A→B→ステップcの順とする） |
| 「商品を選んだが入力を取りやめたい」場合 | 数量0では申請できなくなるため、取りやめる場合は商品名（lookup）を解除して行を空にする必要がある。lookupの解除が操作として難しくないかは、実機で確認する（運用上の注意点。矛盾ではない） |
| 数量だけ入力されて商品が未選択の行 | 商品未選択なので本チェックの対象外（要求されていない）。単価がなく価格が0になるため、運用上おかしいが、本ステップでは扱わない（必要なら別途） |

## 実装方針

### 1. `src/forms/annual-contract-change-logic.ts`（純粋ロジック、ユニットテスト対象）
- 定数`TEST_ENV_LICENSE_PRODUCT_CODE_KEYWORD = "CCTLST0000"`
- 関数`findInvalidAddedQuantities(addedRows: { productCode: unknown; productName: unknown; quantity: unknown }[])`：商品が選択されている行（商品コードまたは商品名が空・空白のみでない行）のうち、数量が未入力・空白のみ・数値でない・0以下・小数の行（行番号・商品名つき）を返す
- 関数`hasTestEnvLicenseProduct(productCodes: unknown[]): boolean`：商品コードに`CCTLST0000`を含むものが1つでもあるか（`null`・`undefined`・空文字は無視）
- 関数`findEmptyTestEnvUrlFields(values: { firstChoice: unknown; secondChoice: unknown; thirdChoice: unknown }): string[]`：空・空白のみの項目の表示名（「テスト環境のURL希望①」等）を返す

### 2. `tests/forms/annual-contract-change-logic.test.ts`（テスト追加）
- `findInvalidAddedQuantities`：数量が1以上の整数→対象外／未入力・空白・`null`・`undefined`・0・負数・小数・数値でない→不正として返す／商品コードのみ・商品名のみが入力された行も対象／商品が未選択（コード・名前とも空）の行は数量が不正でも対象外／複数行のうち不正な行のみ（行番号つき）／文字列・数値のどちらでも同じ結果
- `hasTestEnvLicenseProduct`：該当コードを含む（前後に文字がある場合も）／含まない／空・`null`／複数行のうち1行のみ該当
- `findEmptyTestEnvUrlFields`：3つとも入力済み→空配列／一部未入力→該当項目のみ／全て未入力→3項目／空白のみ→未入力扱い／`null`・`undefined`→未入力扱い

### 3. `src/forms/annual-contract-change.ts`
- 定数：`TEST_ENV_URL_FIRST_CHOICE_PART_ID`・`..._SECOND_...`・`..._THIRD_...`（`ADDED_PRODUCT_CODE_PART_ID`・`ADDED_PRODUCT_NAME_PART_ID`・`ADDED_PRODUCT_QUANTITY_PART_ID`は既存）
- 関数`validateAddedProductQuantities(data)`：明細テーブルの各行から商品コード・商品名・追加商品契約数を集め、`findInvalidAddedQuantities`の最初の1件があれば`alert()`＋`false`
- 関数`validateTestEnvUrls(data)`：各行の商品コードを`hasTestEnvLicenseProduct`で判定し、該当すれば3パーツの値を`findEmptyTestEnvUrlFields`に渡し、未入力があれば未入力項目名を含む文言で`alert()`＋`false`
- `form.confirm`/`form.submit`のチェーンに連結：`blockSubmissionIfDataIssueDetected() && validateChangeApplyMonth(data) && validateChangeApplyMonthDiff(data) && validateAddedProductProratedMonths(data) && validateAddedProductQuantities(data) && validateTestEnvUrls(data) && validateOptionUserCounts(data)`
- ファイル先頭コメントに本ステップの参照を追記

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm test` / `npm run build`を実行。純粋関数はユニットテストで網羅
2. ユーザーが検証環境（年額版フォーム）で以下を確認

   - 追加した行を消して商品を変更した場合（テスト環境ライセンスでなくなった場合）に、再び不要になること
   - ステップa〜d・2c-g・2c-hの回帰確認
