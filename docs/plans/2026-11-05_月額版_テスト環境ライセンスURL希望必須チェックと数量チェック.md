# 月額版へのテスト環境ライセンスURL希望必須チェック（★1）・数量チェックの適用と共通化

[全体計画](2026-08-24_顧客ポータルカスタマイズ全体計画.md)フェーズ1のd（テスト環境ライセンス／コラボフォームの条件付き必須。判別ロジック未確定のため保留中だった）のうち、★1（テスト環境ライセンス）の分と、年額版で追加した新規追加行の数量チェックを、月額版にも適用する。あわせて、年額版専用ファイルにあるフォーム非依存の汎用ロジックを共通モジュールへ移す。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。

## 承認状況

承認済み（2026-11-05、共通モジュールへの移動（リファクタリング）を含む）

## 背景

年額版のステップ3-1（[計画](2026-11-02_フェーズ4ステップ3-1_テスト環境ライセンス申込み時のURL希望必須チェック.md)）で、次の2つを実装し、実機確認済み（2026-11-05）。

- テスト環境ライセンス（新規追加商品の商品コードに`CCTLST0000`を含む）が追加された場合、テスト環境のURL希望①〜③を必須とする（確認・送信時にブロック）
- 商品が選択された全新規追加行で、追加商品契約数が1以上の整数でなければ警告して止める

月額版の[要求事項](../forms/requirements/【クラウド版】注文書兼利用申込書（月額：契約変更）.md)の★1は年額版と同一の文言で、パーツID（`fidTestEnvUrlFirstChoice`・`fidTestEnvUrlSecondChoice`・`fidTestEnvUrlThirdChoice`・`fidAddedProductCode`・`fidAddedProductName`・`fidAddedProductQuantity`）も同一であることをパーツ構造JSONで確認した。月額版には、これらの検証はまだない（3パーツとも`required: false`、`fidAddedProductQuantity`も`required: false`）。月額版のフェーズ1のdは、年額版で判別方法（商品コード）が確定したため、★1の分は着手できる。

## 対象と対象外

| 項目 | 本計画 |
| --- | --- |
| ★1（テスト環境ライセンス）のURL希望必須チェック | 対象 |
| 新規追加行の数量チェック（商品選択済み行は1以上の整数） | 対象 |
| 汎用ロジックの共通モジュールへの移動 | 対象（リファクタリング） |
| ★2・★3（コラボフォーム） | 対象外（判別方法・サブドメインの取得元が未確認。年額版と同じ） |
| 「変更後差分契約数」パーツの月額版への追加 | 対象外（別計画。追加時は、解約ロック再適用（ステップbの案A）を必ずセットにする） |
| 期中の解約・減数・増数の制限 | 対象外（年額契約固有。月額版は期中でも変更できる運用か未確認） |

## 事前調査の結果（Reasoning）

| 項目 | 状態 |
| --- | --- |
| 年額版の実装 | `annual-contract-change-logic.ts`に、`TEST_ENV_LICENSE_PRODUCT_CODE_KEYWORD`・`findInvalidAddedQuantities`・`hasTestEnvLicenseProduct`・`findEmptyTestEnvUrlFields`（と内部ヘルパー`isBlankValue`）があり、`tests/forms/annual-contract-change-logic.test.ts`にテストがある。いずれもフォーム固有のIDに依存しない純粋ロジック |
| 共通モジュールの方針 | フェーズ4計画の「アーキテクチャ方針」で、フォーム固有のフィールドコード・パーツIDに依存しない汎用ロジックは`contract-change-shared-logic.ts`に置くと決めている。年額版ステップ3-1では、月額への展開が未定だったため年額専用ファイルに置いたが、月額版へ適用する今回、共通モジュールへ移す |
| 月額版の構造 | `monthly-contract-change.ts`に`ADDED_PRODUCT_QUANTITY_PART_ID`・`ADDED_PRODUCT_CATEGORY_PART_ID`はあるが、`fidAddedProductCode`・`fidAddedProductName`・URL希望3パーツのIDの定数は未定義。`form.confirm`/`form.submit`のチェーンは、`blockSubmissionIfDataIssueDetected() && validateChangeApplyMonth(data) && validateOptionUserCounts(data)` |
| 既存契約のテスト環境ライセンス | 月額版でも、★1の対象は新規追加行のみ（年額版と同じ。要求事項が「新規追加された場合」のため） |

## 実装方針

### 1. 共通モジュールへの移動（リファクタリング、動作変更なし）
- `src/forms/contract-change-shared-logic.ts`に、`annual-contract-change-logic.ts`から次を移す（関数のシグネチャ・挙動は変更しない）
  - `TEST_ENV_LICENSE_PRODUCT_CODE_KEYWORD`
  - `isBlankValue`（内部ヘルパー）
  - `AddedLineItemForQuantityValidation`・`InvalidAddedQuantity`・`findInvalidAddedQuantities`
  - `hasTestEnvLicenseProduct`
  - `findEmptyTestEnvUrlFields`
- `annual-contract-change-logic.ts`からは上記を削除し、`annual-contract-change.ts`のimport元を共通モジュールに変更する（`annual-contract-change-logic.ts`にある`CHANGE_APPLY_MONTH_DIFF_ABNORMAL_THRESHOLD`・`findMidTermChanges`・`findProratedMonthsMismatches`などの年額固有ロジックは移さない）
- `tests/forms/annual-contract-change-logic.test.ts`から該当するテスト（`findInvalidAddedQuantities`・`hasTestEnvLicenseProduct`・`findEmptyTestEnvUrlFields`のdescribe）を、`tests/forms/contract-change-shared-logic.test.ts`へ移す（テストの内容・件数は変えない）
- 年額版の既存動作が変わらないことは、移動後も全テストが通ること、および年額版の実機での回帰確認で担保する

### 2. 月額版への適用（`src/forms/monthly-contract-change.ts`）
- 定数を追加：`ADDED_PRODUCT_CODE_PART_ID`・`ADDED_PRODUCT_NAME_PART_ID`・`TEST_ENV_URL_FIRST_CHOICE_PART_ID`・`TEST_ENV_URL_SECOND_CHOICE_PART_ID`・`TEST_ENV_URL_THIRD_CHOICE_PART_ID`（`ADDED_PRODUCT_QUANTITY_PART_ID`は既存）
- 関数`validateAddedProductQuantities(data)`・`validateTestEnvUrls(data)`を追加（年額版の同名関数と同じ構成・同じ警告文言）
- `form.confirm`/`form.submit`のチェーンを、`blockSubmissionIfDataIssueDetected() && validateChangeApplyMonth(data) && validateAddedProductQuantities(data) && validateTestEnvUrls(data) && validateOptionUserCounts(data)`に変更（年額版と同じ並び：数量→URL希望→ユーザー数整合性）
- ファイル先頭コメントに本計画の参照を追記

### 検証ルール（年額版と同一）
- 数量チェック：商品が選択されている新規追加行（商品コードまたは商品名が入力）の追加商品契約数が、1以上の整数でなければ、`alert()`＋申請ブロック。文言：「追加商品『○○』の追加商品契約数が未入力または0です。1以上の数量を入力してください。」
- ★1：新規追加行に、商品コードに`CCTLST0000`を含む行が1つでもあれば、`fidTestEnvUrlFirstChoice`・`fidTestEnvUrlSecondChoice`・`fidTestEnvUrlThirdChoice`のすべてが入力済みでなければ、`alert()`＋申請ブロック。文言：「テスト環境ライセンスを追加する場合は、テスト環境のURL希望①〜③をすべて入力してください。（未入力：○○）」
- 警告は1回の確認・送信操作で1つずつ表示（数量→URL希望の順）

## ユーザー確認事項（2026-11-05、すべて回答済み・OK）

1. **月額版でも★1の必須範囲は同じ3項目**（URL希望①〜③。お試し環境のURLは対象外）でよいか。
2. **月額版にも新規追加行の数量チェックを適用してよいか**（商品を選択して数量が未入力・0の申請は、今後ブロックされる）。
3. **共通モジュールへの移動（リファクタリング）**を、本計画の承認時に合わせて承認いただけるか。実機確認済みの年額版のコードに手を入れる（動作変更なし）。

## 今回やらないこと（切り出し）

- 「変更後差分契約数」パーツの月額版への追加（別計画。コラボフロー側のパーツ追加を伴う）
- ★2・★3（コラボフォーム）
- 年額版・月額版の変更適用年月の検証で、空値が`Number("")`で0になる潜在的な課題の修正（別途、確認のうえ小さな修正として実施）

## 影響範囲

- 月額版：`monthly-contract-change.ts`への追加のみ。インスタンス名UI・kintone連携・解約連動・変更適用希望年月・ユーザー数整合性の既存ロジックには影響しない。**数量チェックにより、商品を選択して数量が未入力・0の新規追加行がある申請は、今後ブロックされる**（従来は価格0のまま申請できていた）。取りやめたい行は商品名（lookup）を解除して行を空にする必要がある
- 年額版：import元の変更のみ（動作変更なし）
- 共通モジュール：関数の追加のみ。既存関数への影響なし

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm test` / `npm run build`を実行。テスト件数は移動の前後で変わらないこと（移動分のテストが共通側で通ること）
2. ユーザーが検証環境で以下を確認
   - 月額版：商品を選択して数量が未入力・0のまま「確認」を押すと、商品の種類を問わず警告が出て進めないこと。数量を1以上にすると進めること
   - 月額版：テスト環境ライセンス（商品コードに`CCTLST0000`を含む商品）を新規追加し、URL希望が1つでも未入力なら、警告に未入力の項目名が出て進めないこと。すべて入力済みなら進めること
   - 月額版：テスト環境ライセンス以外の商品のみを追加した場合は、URL希望が空でも進めること
   - 月額版：ステップa〜b・e・fの回帰確認（インスタンス名UI、解約連動・背景色、ユーザー数整合性、変更適用希望年月）
   - 年額版：ステップ3-1・3-2・2c-g・2c-hの回帰確認（共通化による動作変更がないこと。特に数量チェックとURL希望必須チェック）
