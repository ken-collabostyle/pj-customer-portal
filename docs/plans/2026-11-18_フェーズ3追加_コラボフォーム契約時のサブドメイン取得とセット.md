# フェーズ3追加 選択中インスタンスのサブドメイン取得とセット（月額・年額）

**状態：保留（2026-11-18、サブドメインは手入力で進めると決定。本計画のサブドメイン自動取得は、業務支援チームの確認結果が出るまで実装しない）**

## 0. 保留の経緯（2026-11-18、ユーザー回答）

セキュリティ上の懸念（インスタンス名をJS側から渡すため、書き換えれば他社のサブドメインを参照できてしまう）を許容できないため、**サブドメインは手入力で進める**と決定した。

- 今回のカスタマイズでは、`fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain` を自動セットしない。パーツはそのまま残し、入力はユーザーが行う。コード変更は発生しない。
- 将来の方針：プレイス_サブドメイン管理アプリに「顧客番号」フィールドを追加できれば、プロキシ側でログインユーザーの拡張属性にある顧客番号と突き合わせて、安全に取得できる。追加が可能かは、ユーザーが業務支援チームに確認する。
- 留意点：[README](../kintone/README.md)の通り、「ユーザー拡張フィールドをプロキシリクエストに差し込む機能」は、コラボフォームに実装されていない（2026-08-25時点。現在の状況は要確認）。顧客番号を追加できても、この機能が使えることが前提になる。
- 再開条件：上記が実現できると確認できた時点で、本計画のステップ1〜5を、検索キーを顧客番号に読み替えて見直し、再度承認を得る。

以下のQ2〜Q5・ステップは、再開時の参考として残す（インスタンス名で検索する案を前提としており、再開時に見直しが必要）。

## 1. 目的と確定事項（2026-11-18、ユーザー回答）

kintoneの「プレイス_サブドメイン管理」（アプリID: 81、APIキー認証）から、選択中インスタンスのサブドメインを取得して `fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain` にセットする。月額版・年額版の両方に適用する。

| 項目 | 確定内容 |
|---|---|
| 検索キー | `インスタンス名`（選択中のインスタンス名で検索） |
| 絞り込み | `ユーザー削除日` が空のレコードのみ対象。**それでも複数ある場合はエラー** |
| セットの条件 | **コラボフォームの契約・新規追加・解約の判別はしない**（Q1の回答）。サブドメイン管理アプリに該当レコードがあれば、常に取得してセットする。レコードの有無が、コラボフォームの契約情報の有無に相当する |
| 2パーツの違い | なし（取得内容・表示/編集可否とも同じ扱い） |
| 適用範囲 | 月額版・年額版の両方 |
| プロキシAPI | 名称は本計画で提案。管理画面での作成はユーザーが行う |
| `.env.example` | キーを追加してよい（承認済み） |
| `fidAddedProductName` のマスタ参照 | `master_parts_key`・`master_id` は入っているのが正。以前が誤りだったと扱い、対応不要 |

> 以前の回答「コラボフォームの契約・新規追加・解約時のみ」は、Q1の回答（判別しない）により上書きされた。

## 2. 確認が必要な事項（Q1の回答を受けた案。承認時に確認をお願いします）

- **Q2 取得とセットのタイミング**：案は、インスタンスが決まったとき（初期表示のデフォルトインスタンス、およびプルダウンでの切り替え時）に取得してセットする。インスタンスごとにプロキシを1回呼び出す。
- **Q3 セット先**：案は、**両パーツ（`fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain`）に同じ値をセット**する（2パーツに違いがないため）。
- **Q4 エラー時の挙動**：案は次の通り。
  - **0件**：エラーにしない。パーツは空のままにする（コラボフォーム未契約のインスタンスは0件になるため）。
  - **複数件**（`ユーザー削除日` が空のもの）：エラー。アラートを表示し、確認・送信をブロックする。
  - **通信失敗・プロキシエラー**：エラー。アラートを表示し、確認・送信をブロックする（既存の `kintoneCallFailed` と同じ扱い）。
  - 通信失敗でブロックしてよいか（非コラボフォーム顧客でも、サブドメイン管理アプリの障害で申請できなくなる）、ブロックせず空のままにするかを確認したい。
- **Q5 編集可否**：案は、セットした値を入力不可（readOnly）にし、0件で空のときも入力不可のままにする。0件で空のとき、手入力を許可するかを確認したい。
- **注意（セキュリティ）**：このアプリは顧客に依存しないため、検索条件のインスタンス名をJS側から渡す必要がある。JSの値は書き換え可能で、他社のサブドメインを参照できてしまう。ただし対象が契約DBの取得結果に含まれるインスタンス名に限られることと、サブドメイン自体の機密度が低いことから許容できるか確認したい。

## 3. 事前調査の結果（Reasoning）

- プロキシAPI設定はフォーム単位のため、月額・年額でエンドポイントを分ける必要がある（[README](../kintone/README.md)、2026-10-02判明）。既存の命名は `kintone-contract-db`（月額）・`kintone-contract-db-annual`（年額）。
- 本アプリ用は命名規則に合わせ、**`kintone-place-subdomain`（月額版）・`kintone-place-subdomain-annual`（年額版）** を提案する。
- 設定案（管理画面）：メソッドGET、パス `/k/v1/records.json`、クエリは `app=81` のみ固定、ヘッダー `X-Cybozu-API-Token` にAPIトークン。**`query` は管理者設定を優先する仕様**のため、管理画面側では `query` を設定せず、JS側から `options.query` で渡す（[proxy-api.md](../collaboform-js-api/proxy-api.md)）。`kintone-license-type-master` と同じ考え方。
- 既存のプロキシ呼び出しは `form.show` 内の `collaboform.proxy.call` に集約され、インスタンスごとの反映は `applyInstanceData`（インスタンス名を受け取り、表示項目と明細をセットする関数）が担う。プルダウン切り替えも同関数を経由する。サブドメインの取得は、この関数の延長で実装できる見込み。
- 判別が不要になったため、`区分`・商品コードによる判定や、チェックボックス・商品選択のイベント連動は不要。

## 5. 影響範囲

- 既存の契約情報取得・解約連動・各種チェックには手を入れない。インスタンス確定時のプロキシ呼び出しと、2パーツの値セットを追加するのみ。
- **フォーム初期表示時とインスタンス切り替え時のプロキシ呼び出しが1回ずつ増える。** ローディング表示の解除タイミングを、サブドメイン取得の完了後にするかを、実装時に整理する。
- `fidCollaboformSubdomain`・`fidCollaboformCurrentSubdomain` は、現状コードから参照されていない。値をセットすると、申請データ（コラボフローの申請内容）に入る。
- 月額版は最新のパーツ構造JSON・Excelが未提供。ステップ4の前に、月額版の2パーツの有無・名称の突合が必要。
