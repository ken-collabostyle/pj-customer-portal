## 要求事項（該当箇所抜粋）

> オプションがユーザーライセンス形式の場合、オプションのライセンス数が、ベースライセンスと同じユーザー数になっているかをチェックする。

## 経緯

当初、実装メモの想定方針は「商品マスタの区分情報等でユーザーライセンス形式か判定」だったが、クラウド契約管理DBと商品マスタが直接連携していないことが判明し保留（[全体計画](2026-08-24_顧客ポータルカスタマイズ全体計画.md)「商品マスタ関連の保留事項」参照）。2026-09-11、業務支援チームとの調整により定価取得元は商品マスタからライセンス種類マスタに変更する方針が決定し、あわせてクラウド契約管理DBとの突合キー（`ライセンス種類マスタ読込`⇔`検索ワード`）も確認済み。

その後の調査で、**既存契約行についてはクラウド契約管理DB自体が`区分`フィールドを持っており、ライセンス種類マスタへの追加アクセスなしで本チェックが実装可能**と判明。

新規追加商品分については、当初`fidAddedProductCode`（＝商品マスタのメーカー型番）からライセンス種類マスタの`区分`を引く突合キーが未確定のため保留（e-2として別対応の予定）としていたが、**2026-09-16に保留解消**：ユーザーが業務支援チームと調整し、既存の`fidAddedProductName`lookup設定（コラボフロー側のフォーム設定、REST APIではなくコラボフォームのlookup機能）に商品マスタの`商品区分2`（`文字列__1行__5`）→新設パーツ`fidAddedProductCategory`の対応付けを追加（コミット`5e4876e`、[docs/kintone/商品マスタ.md](../kintone/商品マスタ.md)参照）。これにより新規追加商品分もライセンス種類マスタへの追加アクセスなしで`区分`が取得できるため、**e-2に分けず本計画に統合する**。

## スコープ（2026-09-16更新）

- **対象「区分」**：オプション系すべて（`オプション`／`オプション（ライセンスキー不要）`／`オプション（転記不要）`）。`フォーム`／`フォームOP`は対象外（2026-09-11ユーザー確認済み）
- **対象行**：
  - 既存契約行（`kintone-contract-db`由来、明細テーブル「1. 変更後契約数」列側）
  - 新規追加商品行（`fidAddedProductName`経由、「2. オプション等新規追加」列側）：`fidAddedProductCategory`が自動セットされるようになったため対象に含める
- **解約チェックON（変更後契約数=0固定）の既存契約行**：整合性チェックの対象外とする（意図的な0のため不一致と判定しない。新規追加行には解約チェックに相当する概念がないため対象外の判定は不要）
- **ベース行自体が解約された場合**（基準値が0になる）：オプション側のチェックをスキップする（比較基準が意味を持たないため）
- **新規追加行に「ベース」区分が入力された場合**（本来想定しない操作だが、商品マスタの検索結果次第では発生しうる）：基準値の算出には使わず（基準値は既存契約行側の「ベース」のみを見る）、オプション側のチェック対象にも含めない（想定外入力として無視する）。実機確認で不自然な挙動がないか確認する

## 対象パーツ（パーツ構造JSON・既存コードで確認済み）

- 明細テーブル`tbl_1`の各行
  - 既存契約行側：`fidChangedProductQuantity`（変更後契約数、`LINE_ITEM_COLUMN_PART_IDS.changedQuantity`）、`fidProductCancel`（商品解約、`CANCEL_CHECKBOX_PART_ID`）
  - 新規追加行側：`fidAddedProductQuantity`（追加商品契約数）、`fidAddedProductCategory`（追加商品区分、2026-09-16新設、`fidAddedProductName`のlookupで自動セット）

## データソース

- 既存契約行：[monthly-contract-change-logic.ts:31-42](../../src/forms/monthly-contract-change-logic.ts#L31-L42)の`ContractRecord.category`（クラウド契約管理DBの`区分`フィールド、[クラウド契約管理DB.md](../kintone/クラウド契約管理DB.md)参照）。現状[buildLineItems](../../src/forms/monthly-contract-change-logic.ts#L139-L146)はこの値を`ContractLineItem`へ渡していないため、渡すよう拡張する
- 新規追加行：`fidAddedProductCategory.value`（フォーム上に既にセットされている値をそのまま読み取るだけでよい）

**新規のkintoneアクセス・プロキシAPIエンドポイントはいずれも不要**。

## 実装方針

1. `monthly-contract-change-logic.ts`
   - `ContractLineItem`インターフェースに`category: string`を追加し、`buildLineItems`で`record.category`をセットする
   - 定数`OPTION_CATEGORIES`（`["オプション", "オプション（ライセンスキー不要）", "オプション（転記不要）"]`）を追加
   - 新規の純粋関数`findUserCountMismatches`を追加
     - 入力：
       - `existingRows`：既存契約行データの配列（`category`・`changedQuantity`・`isCancelled`）
       - `addedRows`：新規追加行データの配列（`category`・`quantity`。解約概念なし）
     - ロジック：
       1. `existingRows`からベース行（`category === "ベース"`）を1件検索。存在しない、または`isCancelled === true`の場合は空配列を返す（チェックスキップ）
       2. ベース行の`changedQuantity`を基準値とする
       3. `existingRows`のうち`OPTION_CATEGORIES`に含まれ、かつ解約されていない行で、`changedQuantity`が基準値と一致しないものを抽出
       4. `addedRows`のうち`OPTION_CATEGORIES`に含まれ（`category`が空・「ベース」等はスキップ）、`quantity`が基準値と一致しないものを抽出
       5. 3.と4.を合わせた配列を返す（行の種別・行番号が呼び出し側で分かるよう、各要素に`source: "existing" | "added"`と`rowIndex`を含める）
   - ユニットテスト（既存のテストファイル）に、一致／不一致（既存・新規追加それぞれ）／解約行除外／ベース解約時スキップ／新規追加行が「ベース」区分の場合の無視、の各ケースを追加
2. `monthly-contract-change.ts`
   - `form.confirm`／`form.submit`ハンドラーで呼び出す新規関数`validateOptionUserCounts(data)`を追加
     - 明細テーブル（`tbl_1`）の各行から、既存側は`category`（`applyLineItemsToTable`時に保持する行ごとのキャッシュ）・`fidChangedProductQuantity.value`・`fidProductCancel.value`、新規追加側は`fidAddedProductCategory.value`・`fidAddedProductQuantity.value`を集めて`findUserCountMismatches`に渡す
     - 不一致行があれば`alert()`で警告し、`false`を返して送信をブロックする
   - 既存の`blockSubmissionIfDataIssueDetected`とは別関数として追加し、`form.confirm`/`form.submit`内で両方の条件をチェックする（既存条件への影響なし）

### 行ごとの`category`の保持方法（実装時の詳細）

既存契約行には`区分`を表示・保持する専用パーツが存在しない（表示上は`fidChangedProductName`等のみ）。`applyLineItemsToTable`実行時に、行インデックス→`category`の対応を保持する内部配列（例：`let currentLineItemCategories: string[] = []`、ステップaの`activeMonthlyRecordsCache`と同様のモジュールレベルキャッシュ）を新設し、インスタンス切り替え時（`applyInstanceData`）に更新する。新規追加行側は`fidAddedProductCategory`がフォーム上の値としてそのまま存在するため、キャッシュは不要。

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm run test`を実行し、`npm run build`でdist生成を確認。純粋ロジック（`findUserCountMismatches`）はユニットテストでケースを網羅
2. ユーザーが検証環境で以下を確認
   - 既存オプション行の変更後契約数がベースと一致する場合、申請可能なこと
   - 既存オプション行の変更後契約数をベースと異なる値に変更すると、確認・送信時に警告が表示され申請がブロックされること
   - 該当オプション行の「解約」をチェックすると、その行は不一致判定の対象から外れること
   - ベース行自体を解約した場合、他のオプション行の不一致があっても警告が出ないこと（チェックスキップ）
   - 「オプション等新規追加」欄でオプション系商品を追加し、追加商品契約数をベースと異なる値にすると警告が表示されること
   - `fidAddedProductCategory`に実際にセットされる値が、想定する「オプション」等の表記と一致していること（商品マスタの`商品区分2`の実データを確認）
   - 複数インスタンス切り替え時も`category`の対応関係が正しく更新されること
