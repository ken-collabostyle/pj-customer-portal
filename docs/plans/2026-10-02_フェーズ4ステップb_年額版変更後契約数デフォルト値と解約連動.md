# フェーズ4 ステップb 詳細計画：年額版変更後契約数のデフォルト値／解約チェック連動

[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)フェーズ1のステップb。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。月額版[ステップb計画](2026-09-02_フェーズ1ステップb_変更後契約数デフォルト値と解約連動.md)と同じ実装パターンを踏襲する。

## 承認状況

承認済み（2026-10-02）

## 要求事項（該当箇所抜粋）

> 「解約」がチェックONされた場合「契約後契約数」に「0」をセット。「契約後契約数」は変更不可となる。「解約」のチェックがOFFになると、元の契約数が再セットされる。

「変更後契約数」のデフォルト値（＝現商品契約数と同じ値をセット）自体はステップaで実装済み（[annual-contract-change.ts](../../src/forms/annual-contract-change.ts)の`applyLineItemsToTable`）。ステップbは「解約」チェックボックスとの連動部分のみが対象。

## スコープ（フェーズ4計画の「フル年額商品のみ対象」について）

フェーズ4計画では本ステップを「フル年額商品のみ対象。『nヶ月分』商品の除外はフェーズ2で追加」としている。現時点では商品マスタ連携（フェーズ2a）が未解消のため、JS側で「nヶ月分」商品かどうかを判定する手段がない。そのため、**本ステップでは月額版と全く同じロジックをすべての明細行に適用**し（商品種別による分岐は行わない）、「nヶ月分」商品の除外（減数・解約禁止）は商品マスタ連携が解消し次第、フェーズ2の別ステップとして追加する。この順序はユーザー承認済みの[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)のフェーズ構成に基づく。

## 対象パーツ（月額版と同一、パーツID設計で確認済み）

- `fidProductCancel`：明細テーブル内のチェックボックス。`checked_comment: "解約"` / `unchecked_comment: "継続"`（月額版と完全一致）
- `fidChangedProductQuantity`：変更後契約数（既存定数`LINE_ITEM_COLUMN_PART_IDS.changedQuantity`）
- `fidCurrentProductQuantity`：現商品契約数（既存定数`LINE_ITEM_COLUMN_PART_IDS.currentQuantity`）。解約チェックOFF時の復元元として使う

## 実装方針

月額版[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)のステップb実装をそのまま`annual-contract-change.ts`に複製する（DOM操作を含むため、フェーズ4計画のアーキテクチャ方針により共通化せず複製する対象）。

1. 定数`CANCEL_CHECKBOX_PART_ID = "fidProductCancel"`・`CANCEL_CHECKED_VALUE = "解約"`を追加
2. `form.fidProductCancel.change`イベントを新設。`data.row_index`（1始まり）で対象行を特定し、対象行の`fidProductCancel`の値を判定
   - `"解約"`（チェックON）：同じ行の`fidChangedProductQuantity.value`に`"0"`をセットし、入力欄をロック
   - `"継続"`（チェックOFF）：同じ行の`fidChangedProductQuantity.value`に`fidCurrentProductQuantity.value`を再セットし、ロックを解除
3. 「変更不可」の実現：月額版と同じ非公式DOM操作パターンで、`setChangedQuantityFieldLocked`関数を追加（ネイティブinput要素ID規則`table:{row_index}:fidChangedProductQuantity`で取得し`readOnly`を切り替え）
4. 取得失敗時（DOM構造不一致）は新規フラグ`cancelQuantityLockFailed`を立て、`alert()`表示のうえ`blockSubmissionIfDataIssueDetected`で申請をブロックする（月額版のフェイルセーフパターンを踏襲）
5. 初期表示時（`form.show`）の解約チェック状態は常に未チェックのため、初期ロード時点でのロック処理は不要

## 実装するファイル（変更）

- `src/forms/annual-contract-change.ts`：上記イベントハンドラーとロック処理関数を追加。`annual-contract-change-logic.ts`側の変更は不要（DOM・collaboform API依存のロジックのため、既存方針通りユニットテスト対象外。月額版ステップbと同じ扱い）

## 今回やらないこと（切り出し）

- ステップc（オプションのユーザー数整合性チェック）・ステップd（変更適用希望年月）は別途計画する
- 「nヶ月分」商品の減数・解約禁止（フェーズ2b）：商品マスタ連携解消後に別ステップとして追加
- 「同月内の減数不可」チェック：月額版同様、判定データソース未確定のため対象外のまま

## 影響範囲

- `annual-contract-change.ts`内の追加のみ。既存のインスタンス名UI・kintone連携処理（ステップa）には影響しない
- 明細テーブル内の別パーツ（`fidAddedProductQuantity`等の追加商品側）には影響しない
- 月額版（`monthly-contract-change.ts`）への影響なし

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm run test` / `npm run build`を実行
2. ユーザーが検証環境（年額版フォーム）で以下を確認
   - 既存契約行の「解約」チェックをONにすると、同じ行の「変更後契約数」が0になり入力不可になること
   - 「解約」チェックをOFFに戻すと、「変更後契約数」が現商品契約数の値に戻り入力可能になること
   - 複数行でチェックのON/OFFを行っても他行に影響しないこと
   - （参考確認）「nヶ月分」商品の行でも同じ挙動になること（現時点では商品種別による制限がないことの確認。フェーズ2で制限を追加する前提の暫定挙動）

## 実機確認対応：差分パーツの自動計算によるロック解除（2026-10-02）

実機確認で、「解約」チェックON時にいったん変更後契約数がグレーアウトするが、その後入力不可が解除されてしまう不具合が判明。原因は、「変更後差分契約数」（`fidChangedProductQuantityDiff`、`fidChangedProductQuantity`に依存する`calculate`型パーツ）が、解約連動での`fidChangedProductQuantity.value`セットをトリガーに自動再計算され、その際の行の再描画でJSが直接セットした`readOnly`が解除されるためと判明。

**案A（プロダクトと衝突しない対策、今回採用）**：`form.fidChangedProductQuantityDiff.change`イベントをリッスンし、自動計算完了後のタイミングで改めて`setChangedQuantityFieldLocked`を呼び直す。解約チェック状態は新設のキャッシュ`cancelledRowState`（行インデックス→解約チェック状態）に保持し、このイベント発火時にどちらの状態へロックすべきか判定する。フォーム構造の変更は不要。

**案B（案Aで解決しない場合の代替案、ユーザー提案）**：`fidChangedProductQuantityDiff`を`calculate`型から通常の数値パーツに変更し、差分計算をJS側で行う（コラボフロー側のフォーム構造変更を伴うため業務支援チーム連携が必要）。

`npm run lint` / `npm run typecheck` / `npm test`（70件、変更なし）/ `npm run build`で確認済み。**案Aが実機で解決するかはユーザーの実機確認待ち**。解決しない場合は案Bに切り替える。
