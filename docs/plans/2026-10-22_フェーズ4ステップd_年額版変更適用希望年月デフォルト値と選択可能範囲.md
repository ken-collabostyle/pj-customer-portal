# フェーズ4 ステップd 詳細計画：年額版変更適用希望年月のデフォルト値・選択可能範囲

[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)フェーズ1のステップd。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。月額版[ステップf計画](2026-09-02_フェーズ1ステップf_変更適用希望年月デフォルト値と選択可能範囲.md)と同じ実装パターンを踏襲する。

## 承認状況

承認済み（2026-10-22）

## 要求事項（該当箇所抜粋）

> * 当月の年月をデフォルトでセットする。
> * 月末から3日前になったら、翌月以降の月しか選べないようにする
> * 日本の祝日と土日などの一般的な休日を基準に、営業日の計算を行う

月額版と同一文言（[年額版要求事項](../forms/requirements/【クラウド版】注文書兼利用申込書（年額：契約変更）.md)3〜6行目）。

## 事前調査の結果（Reasoning）

| 項目 | 状態 |
| --- | --- |
| 営業日計算ロジック（`isBusinessDay`・`getBusinessDaysOfMonth`・`getCutoffBusinessDay`・`computeEarliestAllowedApplyMonth`・`isApplyMonthSelectionAllowed`） | 共通モジュール[contract-change-shared-logic.ts](../../src/forms/contract-change-shared-logic.ts)に切り出し済み。ユニットテストも整備済み（新規のロジック変更は不要） |

| 月額版の実装 | `form.show`先頭でデフォルト値セット、`validateChangeApplyMonth`を`form.confirm`/`form.submit`に組み込み（[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)） |

したがって**未実装なのは`annual-contract-change.ts`側のデフォルト値セットとバリデーション関数の組み込みのみ**。年額固有の追加仕様（契約期限との関係等）は要求事項に存在しない。

## スコープ

月額版ステップfと同一。

- **デフォルト値**：`computeEarliestAllowedApplyMonth(new Date(), JAPAN_HOLIDAYS)`の結果（当月の最終営業日から3番目の営業日以降は翌月、それ以前は当月。12月→翌年1月の年またぎにも対応）を`fidChangeApplyYear`・`fidChangeApplyMonth`にセット
- **選択制限**：「確認」「送信」時に、選択された年月が最早選択可能年月より前であれば`alert()`＋遷移中止。ドロップダウンの選択肢自体は制限しない（`fidChangeApplyMonth`はMantineのSelectコンボボックスで選択肢が開いた時のみDOMに描画されるため、選択肢削除のDOM操作は脆弱と判断した月額版の方針をそのまま踏襲）
- **値が未入力・数値変換不可の場合**：本チェックはスキップ（必須チェックはフォーム標準機能に委ねる。月額版と同じ）

## 実装方針

変更ファイルは`src/forms/annual-contract-change.ts`のみ（DOM・collaboform API依存のため、アーキテクチャ方針どおり複製）。

1. `contract-change-shared-logic`のimportに`computeEarliestAllowedApplyMonth`・`isApplyMonthSelectionAllowed`を追加し、`./japan-holidays`から`JAPAN_HOLIDAYS`をimport
2. 定数を追加
   - `CHANGE_APPLY_YEAR_PART_ID = "fidChangeApplyYear"`
   - `CHANGE_APPLY_MONTH_PART_ID = "fidChangeApplyMonth"`
   - `CHANGE_APPLY_MONTH_TOO_EARLY_MESSAGE`（月額版と同一文言：「選択された変更適用希望年月では申請できません。当月分は申込期限（当月最終営業日から3営業日前）を過ぎているため、翌月以降を選択してください。」）
3. `form.show`ハンドラーの冒頭（`showLoadingOverlay()`直後）で、kintone呼び出しとは独立に即時デフォルト値をセットする。月額版と同様に`try/catch`で囲み、失敗時は`console.error`・`hideLoadingOverlay()`のうえ再throwする（ローディングが残り続けるのを防ぐ）
4. 関数`validateChangeApplyMonth(data)`を追加（月額版と同一ロジック）
5. `form.confirm`／`form.submit`を`blockSubmissionIfDataIssueDetected() && validateChangeApplyMonth(data) && validateOptionUserCounts(data)`に変更（月額版と同じ並び順）
6. ファイル先頭コメントにステップdの参照を追記

共通モジュール・`annual-contract-change-logic.ts`・テストファイルの変更は不要。

## 今回やらないこと（切り出し）

- `fidChangeApplyMonthDiff`（変更適用月差分）の自動計算・「nヶ月分」商品の妥当性チェック（フェーズ2c、算出式確定待ち）
- ドロップダウン選択肢自体の制限
- 祝日データの更新・拡張（2026〜2035年の既存データのまま）

## 影響範囲

- `annual-contract-change.ts`への追加のみ。ステップa〜c（インスタンス名UI・kintone連携・解約連動・ユーザー数整合性）の既存ロジックには影響しない
- `form.confirm`/`form.submit`のブロック条件が1つ増える。既存の`blockSubmissionIfDataIssueDetected`・`validateOptionUserCounts`とは独立した関数
- `form.show`の先頭に同期処理が追加されるが、kintone呼び出しの非同期チェーンには影響しない
- 月額版・共通モジュール・祝日データへの影響なし。新規のkintoneアクセス・プロキシAPIも不要

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm test` / `npm run build`を実行
2. ユーザーが検証環境（年額版フォーム）で以下を確認
   - フォームを開いた際、変更適用希望年月に妥当なデフォルト値（当月または翌月）がセットされていること
   - 当月選択可能期限日（当月最終営業日から3営業日目）より前の日付でアクセスした場合、当月を選択したまま「確認」に進めること
   - 当月選択可能期限日以降にアクセスした場合、当月を選択して「確認」を押すとアラートが出て進めないこと（翌月以降なら進めること）
   - 過去の年月（例：前月）を選択した場合も同様にブロックされること
   - ステップa〜cの回帰確認：インスタンス名UI・契約情報表示、解約連動（ロック・背景色）、オプションのユーザー数整合性チェックが従来どおり動作すること

実機確認の都合上、期限日前後の動作は日付を変えて確認できない場合がある。その場合は、現在日付に対する期待値を[ステップf計画](2026-09-02_フェーズ1ステップf_変更適用希望年月デフォルト値と選択可能範囲.md)と同様にユーザーと確認したうえで判断する（純粋ロジックは共通モジュールのユニットテストで日付別に検証済み）。
