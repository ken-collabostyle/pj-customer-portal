# フェーズ1 ステップb 詳細計画：変更後契約数のデフォルト値／解約チェック連動

[全体計画](2026-08-24_顧客ポータルカスタマイズ全体計画.md)フェーズ1のステップb。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。

## 承認状況

承認済み（2026-09-02）

## 要求事項（該当箇所抜粋）

> 「解約」がチェックONされた場合「契約後契約数」に「0」をセット。「契約後契約数」は変更不可となる。「解約」のチェックがOFFになると、元の契約数が再セットされる。

「変更後契約数」のデフォルト値（＝現商品契約数と同じ値をセット）自体はステップaで実装済み（[monthly-contract-change.ts](../../src/forms/monthly-contract-change.ts)の`applyLineItemsToTable`）。ステップbは「解約」チェックボックスとの連動部分のみが対象。

## 対象パーツ（パーツ構造JSONで確認済み）

- `fidProductCancel`：明細テーブル内のチェックボックス。`checked_comment: "解約"` / `unchecked_comment: "継続"`（[docs/forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json:158-167](../forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json#L158-L167)）。[parts-reference.md](../collaboform-js-api/parts-reference.md)の仕様により、`parts.value`はチェック時「解約」・未チェック時「継続」という文字列で取得できる
- `fidChangedProductQuantity`：変更後契約数（既存定数`LINE_ITEM_COLUMN_PART_IDS.changedQuantity`）
- `fidCurrentProductQuantity`：現商品契約数（既存定数`LINE_ITEM_COLUMN_PART_IDS.currentQuantity`）。解約チェックOFF時の「元の契約数」の復元元として使う（ステップa実装時から「変更後契約数の初期値＝現商品契約数」という前提が既にあるため、復元先もこれに合わせる。ユーザーが解約チェック前に変更後契約数を手入力していた場合はその値ではなく現商品契約数に戻る仕様とする）

## 実装方針

1. [docs/collaboform-js-api/events-reference.md](../collaboform-js-api/events-reference.md)の`form.<パーツID>.change`イベント（`form.fidProductCancel.change`）を新設。明細パーツのため`data.row_index`（1始まり）で対象行を特定できる（公式API）
2. イベントハンドラー内で対象行の`fidProductCancel`の値を判定
   - `"解約"`（チェックON）：同じ行の`fidChangedProductQuantity.value`に`"0"`をセットし、入力欄をロック（下記3.）
   - `"継続"`（チェックOFF）：同じ行の`fidChangedProductQuantity.value`に`fidCurrentProductQuantity.value`（現商品契約数）を再セットし、入力欄のロックを解除
3. 「変更不可」の実現：[parts-reference.md:101](../collaboform-js-api/parts-reference.md#L101)により`parts.enabled`は設定不可のため、ステップaの単一インスタンス時ロック（[lockInstanceNameField](../../src/forms/monthly-contract-change.ts#L121)）と同じ非公式実装パターン（DOM操作）を踏襲する
   - ネイティブinput要素のID規則`table:{row_index}:fidChangedProductQuantity`（実機フォームHTMLで確認済み）を`document.getElementById`で取得し、`readOnly`プロパティを解約チェックON/OFFに応じてtrue/falseに切り替える
   - 取得失敗時（DOM構造不一致）は新規フラグを立て、`alert()`表示のうえ`blockSubmissionIfDataIssueDetected`で申請をブロックする（ステップaのフェイルセーフパターンを踏襲）
4. 初期表示時（`form.show`）の解約チェック状態は常に未チェック（デフォルト`false`）のため、初期ロード時点でのロック処理は不要と判断する

## 実装するファイル（変更）

- `src/forms/monthly-contract-change.ts`：上記イベントハンドラーとロック処理関数を追加。テストコード（`monthly-contract-change-logic.ts`）側の変更は不要（DOM・collaboform API依存のロジックのため、既存方針通りユニットテスト対象外）

## 今回やらないこと（切り出し）

- ステップc・e・fは別途計画する
- 「同月別途ユーザー追加時の減数不可」チェックは商品マスタ関連保留・要検討事項のため対象外

## 影響範囲

- 同ファイル内の追加のみ。既存のインスタンス名UI・kintone連携処理には影響なし
- 明細テーブル内の別パーツ（`fidAddedProductQuantity`等の追加商品側）には影響しない

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm run test`を実行し、`npm run build`でdist生成を確認
2. ユーザーが検証環境で以下を確認
   - 既存契約行の「解約」チェックをONにすると、同じ行の「変更後契約数」が0になり入力不可になること
   - 「解約」チェックをOFFに戻すと、「変更後契約数」が現商品契約数の値に戻り入力可能になること
   - 複数行でチェックのON/OFFを行っても他行に影響しないこと
