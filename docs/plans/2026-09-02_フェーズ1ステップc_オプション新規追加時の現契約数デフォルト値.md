# フェーズ1 ステップc 詳細計画：オプション新規追加時の現契約数デフォルト値

[全体計画](2026-08-24_顧客ポータルカスタマイズ全体計画.md)フェーズ1のステップc。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。

## 承認状況

いったん承認されたが、実装着手前のユーザー指摘により**対応不要と判明**（下記「結論（2026-09-10）」参照）。実装は行わずクローズする。

## 要求事項（該当箇所抜粋）

> ここでは新たにオプション系ライセンスを新規追加できる。
> * 新規追加する際の「現契約数」に「0」をデフォルトでセット
> * 新規追加する際の「単価」には「定価」をセットする（※特価（値引）で提供済みだとしても、新規追加時は「定価」での提供となる。）

「単価に定価をセット」は既存のkintone lookup設定で対応済み（実装不要、[実装メモ](../forms/requirements/【クラウド版】注文書兼利用申込書（月額：契約変更）_実装メモ.md)「重要な発見事項1」参照）。ステップcは「現契約数に0をデフォルトセット」のみが対象。

## 対象パーツ（パーツ構造JSONで確認済み）

- `fidAddedProductName`：追加商品名。`type: lookup`（`master_type: kintone`、`master_name: "【検証用】商品マスタ"`）。選択すると`data_placements`により以下が自動セットされる（[docs/forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json:264-277](../forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json#L264-L277)で確認済み）
  - `文字列__1行_`（メーカー型番）→ `fidAddedProductCode`
  - `標準売価`（定価）→ `fidAddedProductUnitPrice`
  - `ラジオボタン_0`（単位）→ `fidAddedProductUnit`
- `fidCurrentProductQuantity`：現契約数（既存定数`LINE_ITEM_COLUMN_PART_IDS.currentQuantity`）。上記lookupの対象外のためJS実装が必要（要求事項の「現契約数に0をデフォルトセット」に対応）。ステップaで実装済みの通り、既存契約行（`fidChangedProductName`側）と新規追加行（`fidAddedProductName`側）は同一テーブルの同一行内の別カラムとして共存する

## 実装方針

1. [events-reference.md](../collaboform-js-api/events-reference.md)の`form.<パーツID>.change`イベント（`form.fidAddedProductName.change`）を新設。明細パーツのため`data.row_index`（1始まり）で対象行を特定できる（公式API、ステップbの`form.fidProductCancel.change`と同じパターン）
2. イベントハンドラー内で、対象行の`fidAddedProductName`の値を判定
   - 値が空文字でない（商品が選択された）：同じ行の`fidCurrentProductQuantity.value`に`"0"`をセット
   - 値が空文字（クリアボタン等で選択解除された）：同じ行の`fidCurrentProductQuantity.value`を空文字にリセット（商品が紐付いていない行に`"0"`が残り続けるのを防ぐため）
3. 「入力不可」化などのDOM操作は不要（`fidCurrentProductQuantity`はステップaの明細表示同様、値をセットするのみで足りる。ユーザーが直接編集できる状態は変更後契約数と異なり要求事項に「変更不可」の指定がないため、readOnly化は行わない）

## 実装するファイル（変更）

- `src/forms/monthly-contract-change.ts`：上記イベントハンドラーを追加。テストコード（`monthly-contract-change-logic.ts`）側の変更は不要（DOM・collaboform API依存のロジックのため、既存方針通りユニットテスト対象外）

## 今回やらないこと（切り出し）

- ステップeは商品マスタ関連の保留により対象外（[全体計画](2026-08-24_顧客ポータルカスタマイズ全体計画.md)「商品マスタ関連の保留事項」参照）
- 「単価に定価をセット」は対応不要（既存lookup設定で対応済み）

## 影響範囲

- 同ファイル内の追加のみ。既存のインスタンス名UI・kintone連携・解約連動・変更適用希望年月処理には影響なし
- 明細テーブル内の既存契約変更用パーツ（`fidChangedProduct*`）には影響しない

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm run test`を実行し、`npm run build`でdist生成を確認
2. ユーザーが検証環境で以下を確認
   - 明細テーブルの「追加商品名」欄でマスター連携から商品を選択すると、同じ行の「現契約数」が0になること
   - 「追加商品名」の選択をクリアすると、「現契約数」が空欄に戻ること
   - 複数行で操作しても他行に影響しないこと
   - 既存契約行（「変更後契約数」側）の表示・動作に影響がないこと

## 結論（2026-09-10）

実装着手前に、ユーザーから「『現契約数』パーツは現状存在しないのでは」との指摘を受け再調査した結果、以下が判明した。

- `fidCurrentProductQuantity`パーツ自体は実在する（パーツ構造JSONで確認済み）が、①「変更後契約数を入力してください」セクションの列としてのみ配置されており、②「オプション等新規追加」セクション（`fidAddedProductName`の行）とは**視覚的に無関係**（ユーザー確認済み）
- 同一テーブルの同一行番号を共有する構造だが、②側の新規追加行に対応する①側の`fidCurrentProductQuantity`へ「0」をセットすると、商品名が空欄のまま「現商品契約数＝0」という実体のない行が①セクションに表示されてしまい、かえって紛らわしい
- `fidChangedProductPrice`の価格計算式も`fidCurrentProductQuantity`を参照しないため、機能的な影響もない

以上より、**現状（空欄のまま）が正しい挙動であり、本ステップの実装は不要**と判断した。[実装メモ](../forms/requirements/【クラウド版】注文書兼利用申込書（月額：契約変更）_実装メモ.md)の該当箇所も修正済み。詳細は[実施記録](../agent-records/2026-09-10_フェーズ1ステップc_対応不要と判断.md)を参照。
