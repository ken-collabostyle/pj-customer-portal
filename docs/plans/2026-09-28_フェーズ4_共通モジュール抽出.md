# フェーズ4 共通モジュール抽出 詳細計画

[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)「アーキテクチャ方針（確定）」に基づく、年額版フェーズ1着手の前提作業。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。

## 承認状況

承認済み（2026-09-28）

## 背景

月額版と年額版で完全に同一のロジック（営業日計算・オプションユーザー数整合性チェック）が存在するため、`monthly-contract-change-logic.ts`から汎用ロジックを`src/forms/contract-change-shared-logic.ts`（新規）へ切り出し、年額版が実装時にそのまま参照できるようにする。関数のシグネチャ・挙動は変更せず、置き場所の移動とimport元の変更のみとする（[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md#L49)のリスク欄参照）。

## 対象関数・移行内容

`src/forms/monthly-contract-change-logic.ts`から以下を`src/forms/contract-change-shared-logic.ts`（新規）へ移動する。

- **営業日計算・変更適用年月**：`toDateKey`（非export内部ヘルパー）、`isBusinessDay`、`getBusinessDaysOfMonth`、`getCutoffBusinessDay`、`ApplyMonth`型、`computeEarliestAllowedApplyMonth`、`isApplyMonthSelectionAllowed`
- **オプションユーザー数整合性チェック**：`OPTION_CATEGORIES`、`isOptionCategory`（非export）、`quantitiesMatch`（非export）、`ExistingLineItemForValidation`型、`AddedLineItemForValidation`型、`UserCountMismatch`型、`findUserCountMismatches`
- **`BASE_CATEGORY`定数**：現在`monthly-contract-change-logic.ts`内で`findBaseRecord`（既存契約行からのベース行検索、この関数自体は移動しない）と`findUserCountMismatches`の両方から参照されている。`findUserCountMismatches`移動に伴い、`BASE_CATEGORY`も共通モジュール側へ移し、`monthly-contract-change-logic.ts`側は`contract-change-shared-logic.ts`からimportして`findBaseRecord`で使う

`MONTHLY_BILLING_CYCLE`・`ACTIVE_CONTRACT_STATUS`・`toContractRecord`・`CONTRACT_DB_FIELD_CODES`・`findBaseRecord`・`buildCurrentContractSummary`・`buildLineItems`等、kintoneフィールドコードやドメインモデルに依存する関数はフォーム固有のため`monthly-contract-change-logic.ts`に残す（フェーズ4計画の「複製する対象」に該当）。

## 影響ファイルと変更内容

1. **`src/forms/contract-change-shared-logic.ts`（新規作成）**
   - 上記関数・型・定数を移動（コードの中身は変更しない）
2. **`src/forms/monthly-contract-change-logic.ts`**
   - 上記の移動対象を削除
   - `findBaseRecord`が使う`BASE_CATEGORY`を`./contract-change-shared-logic`からimport
3. **`src/forms/monthly-contract-change.ts`**
   - `./monthly-contract-change-logic`からのimportのうち、`computeEarliestAllowedApplyMonth`・`findUserCountMismatches`・`isApplyMonthSelectionAllowed`を`./contract-change-shared-logic`からのimportに変更
4. **`tests/forms/monthly-contract-change-logic.test.ts`**
   - `findUserCountMismatches`・`isBusinessDay`・`getBusinessDaysOfMonth`・`getCutoffBusinessDay`・`computeEarliestAllowedApplyMonth`・`isApplyMonthSelectionAllowed`の`describe`ブロックを、新設する`tests/forms/contract-change-shared-logic.test.ts`へ移動（テストケースの内容・アサーションは変更しない）
   - 残す`describe`ブロック（`toContractRecord`・`isActiveMonthlyRecord`・`filterActiveMonthlyRecords`・`extractUniqueInstances`・`filterRecordsByInstance`・`findBaseRecord`・`buildCurrentContractSummary`・`buildLineItems`）のimport文を更新
5. **`tests/forms/contract-change-shared-logic.test.ts`（新規作成）**
   - 4.で移動したテストケースを配置し、importを`../../src/forms/contract-change-shared-logic`に変更

## 影響範囲

- 月額版フォーム（`monthly-contract-change.ts`）の実行時挙動は変更しない（import元の変更のみ、ロジックの中身は無修正）
- 年額版（`src/forms/annual-contract-change-logic.ts`、未作成）は今回のスコープ外。本ステップ完了後、フェーズ1着手時に共通モジュールを参照する形で新規作成する
- 既存のユニットテストがリグレッション検知の役割を果たすため、移動前後でテストケース数・アサーション内容が一致することを確認する

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm test`を実行し、すべて通過することを確認
2. 移動前後でテストケース数が変わっていないこと（テストの追加・削除がないこと）を確認
3. 検証環境での実機確認は不要（ロジックの中身・呼び出し元の実行時挙動を変更しないリファクタリングのため）

## 今回やらないこと

- 年額版フォーム（`annual-contract-change-logic.ts`等）の新規作成（フェーズ1着手時に別途実施）
- `toContractRecord`・明細行構築等、フォーム固有ロジックの共通化（フェーズ4計画で対象外と確定済み）

## 完了（2026-09-28）

計画通り`src/forms/contract-change-shared-logic.ts`を新設し、営業日計算・変更適用年月系（`isBusinessDay`等）とオプションユーザー数整合性チェック系（`findUserCountMismatches`等）、および両者が参照する`BASE_CATEGORY`を移動。`monthly-contract-change-logic.ts`・`monthly-contract-change.ts`のimport元を更新し、テストも`tests/forms/contract-change-shared-logic.test.ts`（26件）と`tests/forms/monthly-contract-change-logic.test.ts`（16件、計42件）に分割。関数の中身・シグネチャは無変更。

`npm run lint` / `npm run typecheck` / `npm test`（42件）/ `npm run build`すべて通過。移動前後でテストケース数が一致することを確認済み（分割後の合計42件は、移動前の単一ファイル42件と一致）。実行時挙動を変更しないリファクタリングのため、検証環境での実機確認は実施していない。
