# フェーズ4 ステップc 詳細計画：年額版オプションのユーザー数整合性チェック

[フェーズ4計画](2026-09-25_フェーズ4_年額契約変更カスタマイズ計画.md)フェーズ1のステップc。CLAUDE.md「1. 推論」の承認ゲートルールに基づき、実装着手前に本計画をユーザーの承認を得てから着手する。月額版[ステップe計画](2026-09-11_フェーズ1ステップe_オプションユーザー数整合性チェック.md)と同じ実装パターンを踏襲する。

## 承認状況

承認済み（2026-10-21）

## 要求事項（該当箇所抜粋）

> オプションがユーザーライセンス形式の場合、オプションのライセンス数が、ベースライセンスと同じユーザー数になっているかをチェックする。

月額版と同一文言（[年額版要求事項](../forms/requirements/【クラウド版】注文書兼利用申込書（年額：契約変更）.md)49行目）。

## 事前調査の結果（Reasoning）

月額版ステップeの実装資産のうち、年額版で再利用できる範囲を確認した。

| 項目 | 状態 |
| --- | --- |
| 判定ロジック`findUserCountMismatches`・`OPTION_CATEGORIES` | 共通モジュール[contract-change-shared-logic.ts](../../src/forms/contract-change-shared-logic.ts)に切り出し済み。ユニットテスト（[contract-change-shared-logic.test.ts](../../tests/forms/contract-change-shared-logic.test.ts)）も整備済み（月額・年額共通で、新規のロジック変更は不要） |
| 既存行の区分（`category`） | 年額版の`buildLineItems`が`ContractLineItem.category`を返す実装済み。`annual-contract-change.ts`の`currentLineItemCategories`にステップa時点で保持済み（現状は未使用） |
| 解約チェックの状態 | 既存パーツ`fidProductCancel`の値と`CANCEL_CHECKED_VALUE`（ステップb実装済み）で判定可能 |
| 新規追加行の区分・数量 | パーツID設計で`fidAddedProductCategory`・`fidAddedProductQuantity`が月額と同一IDで存在。`fidAddedProductName`のlookupで`商品区分2`が`fidAddedProductCategory`に自動セットされる構成も月額と同一（[実装メモ](../forms/requirements/【クラウド版】注文書兼利用申込書（年額：契約変更）_実装メモ.md)16行目） |
| kintone・プロキシ | 新規アクセス不要。`.env`・プロキシAPI管理画面への影響なし |

したがって**未実装なのは`annual-contract-change.ts`側のバリデーション関数と`form.confirm`/`form.submit`への組み込みのみ**。

## スコープ

月額版ステップeと同一（2026-09-11/16ユーザー確認済みの仕様をそのまま適用）。

- **対象区分**：`オプション`／`オプション（ライセンスキー不要）`／`オプション（転記不要）`。`フォーム`／`フォームOP`は対象外
- **対象行**：既存契約行（「変更後契約数」側）と新規追加商品行（「オプション等新規追加」側）の両方
- **解約チェックONの既存行**：対象外（意図的な0のため）
- **ベース行が解約された場合**：オプション側のチェックをスキップ（基準値が0になり意味を持たないため）
- **ベース行が存在しない場合**（テスト環境ライセンス専用インスタンス等）：チェックをスキップ（共通ロジックの既存仕様）
- **新規追加行の区分が空・「ベース」の場合**：対象外

## 実装方針

変更ファイルは`src/forms/annual-contract-change.ts`のみ。月額版[validateOptionUserCounts](../../src/forms/monthly-contract-change.ts#L177-L198)と同じ構成で追加する（DOM・collaboform API依存のため、フェーズ4計画のアーキテクチャ方針どおり共通化せず複製）。

1. `contract-change-shared-logic`から`findUserCountMismatches`をimportに追加
2. 定数を追加
   - `ADDED_PRODUCT_QUANTITY_PART_ID = "fidAddedProductQuantity"`
   - `ADDED_PRODUCT_CATEGORY_PART_ID = "fidAddedProductCategory"`
   - `OPTION_USER_COUNT_MISMATCH_MESSAGE`（月額版と同一文言：「オプションのユーザー数が、ベースライセンスのユーザー数と一致していません。ご注文内容をご確認ください。」）
3. 関数`validateOptionUserCounts(data)`を追加
   - 既存側：明細テーブル各行から`currentLineItemCategories[index]`・`fidChangedProductQuantity.value`・`fidProductCancel.value === CANCEL_CHECKED_VALUE`を集める
   - 新規追加側：各行の`fidAddedProductCategory.value`・`fidAddedProductQuantity.value`を集める
   - `findUserCountMismatches`の結果が空なら`true`。不一致があれば`alert()`で警告し`false`を返す
4. `form.confirm`／`form.submit`のハンドラーを`blockSubmissionIfDataIssueDetected() && validateOptionUserCounts(data)`に変更（`data`引数を受け取る形に変更）。ステップdで追加予定の変更適用希望年月検証は、月額版と同じく`&&`で後から連結する
5. ファイル先頭コメント・`currentLineItemCategories`のコメントを実態に合わせて微修正（「ステップc用」のまま現状は未使用のため、使用箇所を明記）

`annual-contract-change-logic.ts`・共通モジュール・テストファイルの変更は不要（純粋ロジックは月額・年額共通で既にテスト済み。追加のDOM依存コードは月額版ステップe同様、ユニットテスト対象外）。

## 年額版特有の留意点（実機確認での観察項目）

- **「nヶ月分」商品（フェーズ2未対応）**：商品マスタ連携が未解消のため、現時点では区分だけで判定する。「nヶ月分」商品でも区分が`オプション`系であれば、契約数（ユーザー数）をベースと比較する。数量の意味が年額商品と変わらない前提だが、実機で「nヶ月分」オプション行が誤検知されないか確認する。誤検知があればフェーズ2bで読み替え時に再検討する
- **差分パーツ`fidChangedProductQuantityDiff`**：比較に使うのは`fidChangedProductQuantity`（変更後契約数）で、差分パーツは参照しない。ステップbの案A（ロック再適用）にも影響しない

## 今回やらないこと（切り出し）

- ステップd（変更適用希望年月のデフォルト値・選択可能範囲）は別途計画する
- 「nヶ月分」商品の判定・読み替え（フェーズ2）
- 同月内の減数不可チェック（月額版同様、判定データソース未確定のため対象外）

## 影響範囲

- `annual-contract-change.ts`への追加のみ。ステップa（インスタンス名UI・kintone連携）、ステップb（解約連動・ロック）の既存ロジックには影響しない
- `form.confirm`/`form.submit`のブロック条件が1つ増える。既存の`blockSubmissionIfDataIssueDetected`とは独立した関数
- 月額版（`monthly-contract-change.ts`）・共通モジュールへの影響なし

## 確認方法

1. Claudeが`npm run lint` / `npm run typecheck` / `npm test` / `npm run build`を実行
2. ユーザーが検証環境（年額版フォーム）で以下を確認
   - 既存オプション行の変更後契約数がベースと一致していれば、確認・申請できること
   - 既存オプション行の変更後契約数をベースと異なる値にすると、確認・送信時に警告が表示され申請がブロックされること
   - 該当オプション行の「解約」をONにすると、その行は不一致判定の対象から外れること
   - ベース行自体を解約した場合、他のオプション行に不一致があっても警告が出ないこと
   - 「オプション等新規追加」欄でオプション系商品を追加し、追加商品契約数をベースと異なる値にすると警告が表示されること（一致していれば申請できること）
   - `fidAddedProductCategory`に実際にセットされる値が`オプション`等の想定表記と一致していること
   - 複数インスタンス切り替え後も、区分の対応関係が正しく更新され判定が正しいこと
   - 「nヶ月分」商品のオプション行が誤検知されないこと（観察項目。問題があれば実施記録に残しフェーズ2で対応）
   - ステップbの回帰確認：解約チェックON後に「変更後契約数」のロックが維持されること

## 実機確認対応：解約ロック時の背景色（2026-10-21）

ステップb回帰確認の中で、解約ON後のロック自体は維持されているが、`readOnly`だけでは見た目が変わらずロック中と分からない、との指摘があった。`setChangedQuantityFieldLocked`で、ロック時に背景色`rgb(241, 243, 245)`を適用し、アンロック時は空文字で元のスタイルに戻すようにした（定数`LOCKED_FIELD_BACKGROUND_COLOR`）。差分パーツのchangeイベントからも同関数でロックを再適用するため、ステップb案Aの経路でも背景色が再適用される。ユーザー承認のうえ、月額版（`monthly-contract-change.ts`）にも同じ変更を適用した（月額版は本番稼働前）。`npm run lint` / `npm run typecheck` / `npm test`（70件）/ `npm run build`確認済み。

追加の実機確認項目：「解約」ONで背景色が変わりOFFで元に戻ること、複数行で独立していること、差分再計算後も背景色とロックが維持されること（年額・月額の両方）。
