# 実装メモ：【クラウド版】注文書兼利用申込書（月額：契約変更）

[要求事項](【クラウド版】注文書兼利用申込書（月額：契約変更）.md)と[パーツ構造JSON](../json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json)を突合した実装用の対応表・分析メモ。フェーズ1着手前の「推論」フェーズの成果物として作成（[docs/plans/2026-08-24_顧客ポータルカスタマイズ全体計画.md](../../plans/2026-08-24_顧客ポータルカスタマイズ全体計画.md)参照）。

## 重要な発見事項

### 1. 「追加商品名」に商品マスタへのlookupが既に設定済み

`fidAddedProductName`（追加商品名）パーツは`type: lookup`、`master_type: kintone`、`master_name: "【検証用】商品マスタ"`で、以下が自動セットされる設定が**フォーム側に既に存在**する。

| lookup元フィールド（商品マスタ） | セット先パーツ |
|---|---|
| `文字列__1行_`（メーカー型番） | `fidAddedProductCode`（追加商品コード） |

→ 要求事項「新規追加する際の現契約数に0をデフォルトでセット」（`fidCurrentProductQuantity`）はlookupの対象外のため当初JS実装が必要と考えていたが、後日**対応不要と判断**（下表参照）。

**2026-09-11追記**：業務支援チームとの調整により、単位関連パーツ（`fidChangedProductUnit`・`fidAddedProductUnit`）はフォームから削除された。あわせて、このlookup設定から`標準売価`→`fidAddedProductUnitPrice`（単価に定価をセット）・`ラジオボタン_0`→`fidAddedProductUnit`（単位セット）の対応付けも削除されている（[docs/forms/json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json](../json/【クラウド版】注文書兼利用申込書（月額：契約変更）.json)で確認済み）。単位セット削除は今回の対応と整合するが、**単価（定価）の自動セットも意図して削除されたとユーザーに確認済み**（別の方法で対応予定、詳細未定）。「単価に定価をセット」の実装要否は今後の方針確定後に改めて検討する（下表の記載も参照）。

### 1.5. 顧客番号はJavaScript側に一切持たせない（2026-08-25 ユーザー確認）

`kintone-contract-db`での検索キーとなる顧客番号は、セキュリティ上の理由（クライアント側で値を書き換えると他社データを不正取得できてしまうため）でJS側に持たせない設計とする。本来はプロキシAPI側でログインユーザーの拡張フィールドから顧客番号を自動差し込む機能を使う想定だが、**この機能はコラボフォームに現時点で未実装**。暫定対応として、プロキシAPIエンドポイントの管理画面側で固定のテスト用顧客番号を設定する（詳細は[docs/kintone/README.md](../../kintone/README.md)参照）。JSからは`collaboform.proxy.call('kintone-contract-db')`を顧客番号なしで呼び出すだけでよい。

### 2. 「インスタンス名」は現状テキスト型 → プルダウン化にはフォーム変更が必要な可能性

`fidContractedInstanceName`（ご契約中のインスタンス名）は`type: text`。要求事項「複数ある場合はプルダウンで選択」を実現するには、JavaScriptでの値操作だけでなく、**コラボフロー側でパーツ種別をリスト等に変更する作業が別途必要になる可能性がある**（コラボフォームJS APIは既存パーツの値・表示状態の操作が中心で、パーツ種別自体の変更はできないため）。

### 3. 「明細」は表示上2つの表だが、データ構造上は1つの`table`にまとまっている（2026-08-25 ユーザー訂正）

コラボフローでは表示上テーブルが2つに分かれていても、パーツ構造JSON上のデータは1つの`table`（`max_row: 10`）にまとまる。実際の表示は以下の2表に分かれる。

- **表1（既存契約変更用）**：`fidProductCancel`（商品解約）, `fidChangedProductName`（変更後商品名）, `fidChangedProductCode`（変更後商品コード）, `fidChangedProductUnitPrice`（変更後商品単価）, `fidCurrentProductQuantity`（現商品契約数）, `fidChangedProductQuantity`（変更後商品契約数）, `fidChangedProductPrice`（変更後商品価格・自動計算）
- **表2（追加商品用）**：`fidAddedProductName`（追加商品名・lookup）, `fidAddedProductCode`（追加商品コード）, `fidAddedProductUnitPrice`（追加商品単価）, `fidAddedProductQuantity`（追加商品契約数）, `fidAddedProductPrice`（追加商品価格・自動計算）

（2026-09-11追記：`fidChangedProductUnit`・`fidAddedProductUnit`（単位）は業務支援チームとの調整によりフォームから削除済み。上記一覧は削除後の状態を記載）

表1・表2は別々の行を持つのではなく、**同一`table`の1行に表1・表2両方の列がすべて含まれる**（1行＝1レコードに、既存契約変更用フィールドと追加商品用フィールドが同居する）。表示上2つの表に分かれて見えるのはUI側の表示レイアウトであり、JSでのデータ操作時は単一のtable行インデックスとして両方の列を同時に扱う。要求事項の「変更後契約数」は`fidChangedProductQuantity`に対応する。クラウド契約管理DBの`区分`="ベース"の行がベースプランの明細行に相当する。

## 論点の解消状況（2026-08-25 ユーザー確認済み）

1. **インスタンス名のプルダウン化**：フォーム側のパーツ種別は`text`のまま変更せず、JavaScriptで代替UI（`<select>`等をDOM挿入し、選択結果を`parts['fidContractedInstanceName'].value`に反映）を実装する方針。
2. **テスト環境ライセンス／コラボフォームの判別**：現時点では判別ロジックを実装しない（後回し）。フェーズ1では★1・★2・★3の動的必須化は対象外とし、他のステップを先に進める。
3. **「同月別途ユーザー追加」の判定**：データソース未確定。業務支援チームへ確認中のため、[要求事項の要検討事項](【クラウド版】注文書兼利用申込書（月額：契約変更）.md#要検討事項)として保留し、フェーズ2で扱う。フェーズ1のバリデーション実装（ステップe）からは除外する。
4. **明細行の追加不可（Excelフォーム制約）**（2026-09-11ユーザー確認済み）：追加不可前提で運用する。現状（行追加不可）のままでよい。対応不要。
5. **プラン変更時の運用フロー**（2026-09-11ユーザー確認済み）：プラン変更したい場合は「解約」にチェックのうえ、②の新規追加欄で変更後プランを入力してもらう、という理解で確定。実装への追加影響なし（ステップb・cで既に対応済みの「解約」チェック連動・②新規追加のフローがそのまま適用される）。
